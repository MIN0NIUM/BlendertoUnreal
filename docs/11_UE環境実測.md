## 1. 調査方法

1. `mcp__unreal-mcp__list_toolsets` で全 Toolset を列挙。
2. `mcp__unreal-mcp__describe_toolset` で対象 Toolset のツール名・説明・入力スキーマを取得。
3. `mcp__unreal-mcp__call_tool` で**副作用のない読み取り系ツールのみ**を実行
   （`PluginToolset.ListEnabledPlugins` / `AssetTools.list_folders` / `LogsToolset.GetLogEntries` 等）。
4. UE Python は後述の経路（Slate UI のコンソール入力 + 出力ログ読み取り）で
   **値を print するだけの式**を評価。
5. エンジン／プラグインの既定値は、インストール済みエンジンのソース・`.uplugin`・`Config` を
   ファイルシステム上で直接 grep して確認。

アセットの作成・削除・レベル変更・プロジェクト設定変更は一切行っていない。

## 2. 実行できた経路 / できなかった経路

### できた経路

| 経路 | 状態 | 備考 |
|---|---|---|
| MCP `list_toolsets` / `describe_toolset` / `call_tool` | ◎ | 既定 `http://127.0.0.1:8000/mcp`。全 52 Toolset にアクセス可 |
| **UE Python（`py` コンソールコマンド）** | ◎ | `SlateInspectorToolset` で UI 上のコンソール入力欄に `py <式>` を投入 → `LogsToolset.GetLogEntries` で `LogPython` カテゴリを読む。**この往復で任意の Python 式の評価と結果取得が成立した** |
| エンジン／プロジェクトのファイル直読み（Bash / PowerShell） | ◎ | `.uplugin` / `Config/*.ini` / Epic 製 Python 実装の読解 |
| `EditorToolset.LogsToolset.GetLogEntries` | ◎ | カテゴリ・正規表現・件数でフィルタ可。Python の戻り値取得に必須 |

#### `py` コンソールコマンド経路の具体手順（再現用）

1. `SlateInspectorToolset.Observe` で `ref=""`（全ウィンドウ）を監視登録。
2. `SlateInspectorToolset.Snapshot` でウィジェットツリーをテキスト取得し、
   ステータスバーの `Cmd` コンボボックス隣にある `textbox` の ref を特定（実測では `tb3`）。
3. `SlateInspectorToolset.Type` に `ref` / `text="py <1行 Python>"` / `submit=true` を渡す。
4. `EditorToolset.LogsToolset.GetLogEntries` で `category="LogPython"` を読む。
5. 終了後 `SlateInspectorToolset.Unobserve` で監視解除（本調査では解除済み）。

**ハマりどころ（実測）**: UE のコンソールは `|`（パイプ）をコマンド区切りとして解釈するため、
Python 文に `|` を含めると**その位置で文字列が切り捨てられて SyntaxError になる**。
区切り文字には `|` 以外を使うこと。

### できなかった / 存在しなかった経路

| 経路 | 結果 |
|---|---|
| MCP の Python 実行専用 Toolset（`PythonTools` 等） | **存在しない**。52 Toolset 中に該当なし |
| `ProgrammaticToolset.execute_tool_script` を汎用 Python として使う | **不可**。`get_execution_environment` 実測で、許可モジュールは `{copy, time, re, math, datetime, json}` のみ。`unreal` も `sys` も import 不可。用途は「他の登録済みツールの呼び出しをバッチする糊」に限定 |
| MCP 経由の任意コンソールコマンド実行 | **該当ツールなし**。`EditorAppToolset` にあるのは `SearchCVars`（検索のみ）で、`Exec` 系は無い |
| Remote Control API（HTTP / WebSocket） | **プラグインが無効**のため利用不可（§7 参照） |
| Python Remote Execution（UDP マルチキャスト） | **無効**（§7 参照） |

## 5. 「ディスク上の FBX をプロジェクトにインポートする」公式ツールの有無

### 結論

**存在する。ただし `AssetTools` ではなく、メッシュ種別ごとの Toolset にある。**

| 用途 | ツール名（完全名） |
|---|---|
| Static Mesh | `editor_toolset.toolsets.static_mesh.StaticMeshTools.import_file` |
| Skeletal Mesh | `editor_toolset.toolsets.skeletal_mesh.SkeletalMeshTools.import_file` |
| Texture | `editor_toolset.toolsets.texture.TextureTools.import_file` |
| DataTable / CurveTable / StringTable | 各 Toolset の `import_file` |

パラメータは §4.2 / §4.3 の通り。

### ただし、ワンポチツールの本番経路としては不適

インストール済みエンジンの Epic 製実装を直接読んで確認した事実:

`…/Engine/Plugins/Experimental/Toolsets/EditorToolset/Content/Python/editor_toolset/toolsets/static_mesh.py`

```python
options = unreal.FbxImportUI()
options.automated_import_should_detect_type = False
options.import_mesh = True
options.import_as_skeletal = False
options.mesh_type_to_import = unreal.FBXImportType.FBXIT_STATIC_MESH
...
return import_asset(folder_path, asset_name, source_file,
                    options=options, factory=unreal.FbxFactory())
```

`skeletal_mesh.py` も同様に `unreal.FbxImportUI()` + `unreal.FbxFactory()` を固定している。
共通ヘルパ `…/toolsets/asset.py` の `import_asset()` は
`unreal.AssetImportTask` を組み立て `unreal.AssetToolsHelpers.get_asset_tools().import_asset_tasks([task])`
を呼ぶ実装で、docstring に次の明記がある。

> factory を None にするとエンジンが選択し、Interchange 経路が維持される

つまり **公式 MCP のメッシュ `import_file` は、ファクトリを固定することで意図的に
レガシー FBX 経路を使い、Interchange を迂回している**。
加えて次の制約も実装から確認した。

- `replace_existing = False` 固定 → **再インポート（上書き更新）ができない**
- 同名アセットが既に存在すると `RuntimeError` で即失敗
- `save = False` 固定
- 公開されている引数は 3〜7 個のみ。Interchange パイプライン、スケール、座標軸変換、
  法線・接線の扱い、マテリアル命名、LOD グループ、Lightmap UV などは**一切指定できない**

## 10. ワンポチツール実装への示唆

### 結論: インポート処理は **UE Python（Interchange API）で自作する**

| 候補 | 評価 | 理由 |
|---|---|---|
| **UE Python + Interchange** | **◎ 採用** | 下記の理由 |
| 公式 MCP Toolset の `import_file` | × 本番不可 | 下記の理由 |
| 自作 Toolset（`ToolsetDefinition` 派生） | △ 将来の選択肢 | 下記の理由 |

#### 公式 MCP `import_file` を本番経路にできない理由（すべて実装の実測に基づく）

1. **レガシー FBX 経路に固定されている。** `unreal.FbxFactory()` + `unreal.FbxImportUI` を
   ハードコードしており、Interchange を意図的に迂回している。
   設計方針 D-6（お作法をポストプロセスに寄せる）以前に、インポータ自体の選択権がない。
2. **設定の宣言ができない。** 公開引数は 3〜7 個のみ。D-2（設定はプリセット + マニフェストで宣言）を
   満たせない。スケール・軸変換・法線・マテリアル命名・LOD グループ等を一切指定できない。
3. **再インポートができない。** `replace_existing = False` 固定、同名存在で即 `RuntimeError`。
   DCC 側で作り直して再度ワンポチする運用が成立しない。
4. **MCP への実行時依存が生じる。** `docs/91_ツールチェーン提案.md` の方針
  （MCP は開発・検証の補助であり本体の実行時依存にしない）と矛盾する。
   また MCP プラグインは `IsExperimentalVersion: true` / `EnabledByDefault: false`。
5. **D-1（起動方法に依存しない純粋な関数）に反する。** MCP サーバと HTTP クライアントが
   常に必要になる。

#### UE Python + Interchange を採用する理由

1. **必要な API が実機に揃っていることを実測で確認済み。**
   `InterchangeManager`（`get_interchange_manager_scripted` / `import_asset` /
   `scripted_import_asset_async` / `reimport_asset`）、`InterchangeGenericAssetsPipeline`、
   `InterchangeGenericMeshPipeline`、`InterchangePipelineStackOverride`、
   `InterchangeAssetImportData`、`InterchangeSourceData` すべて存在。
2. **D-1 を満たす。** `import_onepochi(manifest_path)` という純粋な Python 関数として書けば、
   MCP / `py` コンソール / `-ExecutePythonScript` / Remote Execution のどこから叩いても同じ。
3. **D-2 を満たす。** Interchange のパイプラインアセットそのものがプリセットになる。
   `InterchangePipelineStackOverride` でマニフェスト由来の設定を宣言的に差し込める。
4. **D-6 を満たす。** インポート後に `StaticMeshTools` 相当の処理
  （Nanite / LOD / コリジョン / マテリアルスロット）を同じ Python 内でポストプロセスできる。
5. **再インポートが設計に入っている。** `reimport_asset` / `InterchangeAssetImportData` があり、
   ソースファイルとの紐づけを保持できる。
6. **`AssetImportTask` 経路も併存可能。** `factory` を `None` にすれば Interchange が選ばれる
  （Epic 自身の `asset.py` の docstring が保証）。段階的実装のフォールバックに使える。

#### 実装レイヤの推奨

```
tools/ue_plugin/onepochi/
  importer.py     # import_onepochi(manifest_path) -> result dict   ← D-1 の純粋関数
  pipeline.py     # マニフェスト → Interchange パイプライン設定への変換   ← D-2
  postprocess.py  # Nanite / LOD / コリジョン / マテリアル割り当て       ← D-6
  entry_console.py # py コンソール / コマンドライン用の薄いラッパ
```

- **公式 MCP Toolset の位置づけ**: **開発・検証用の計測器**として使う。
  `StaticMeshTools.get_triangle_count` / `get_lod_count` / `get_material_slots` /
  `is_nanite_enabled`、`SkeletalMeshTools.get_bone_names` / `get_socket_names` /
  `get_physics_asset` などは、ワンポチ後の結果をテキストで検証するのに最適
  （スクリーンショット不要で CI にも載せやすい）。
- **自作 Toolset は後回しで良い。** `unreal.ToolsetDefinition` を継承して
  `Content/Python/` に置けば自前 Toolset を MCP に露出できることは Epic 実装から確認できたが、
  これは「Claude からワンポチを叩きたくなったとき」の追加レイヤ。コアの Python 関数が先。
- **Remote Control API は現状不要。** Blender → UE のトリガが必要になった段階で、
  `RemoteControl`（HTTP 30010）よりも **Python Remote Execution**（`bRemoteExecution` を有効化。
  `239.0.0.1:6766`）の方が、Python 関数をそのまま呼べるぶん D-1 と相性が良い。
  どちらも**現在は無効なので要有効化**。
- **対応フォーマットの実測事実**: Interchange の `ASSETS` は fbx / glb / gltf / obj / mtlx。
  Blender からの中間フォーマットとして **FBX と glTF の両方が Interchange で扱える**。
  一方 **USD / Alembic は追加プラグイン（`InterchangeOpenUSD` 等）が必要**で、現在は無効。
- **`EditorScriptingUtilities` 系 API は使わない。** 5.8 で非推奨警告が出る（実測）。
  `unreal.get_editor_subsystem(unreal.EditorAssetSubsystem)` 等に寄せる。
