## 1. 位置づけ

マニフェストは **DCC と Unreal Engine の間の唯一の契約** である。

- DCC 側は「どう取り込んでほしいか」をここに宣言する
- UE 側は **マニフェストだけを見て** インポート設定を決める（FBX の中身や人間の操作に依存しない）
- DCC ツールを Houdini に差し替えても、マニフェストが同じなら UE 側は一切変更不要（方針 D-5）
- UE 側のコア処理は `import_from_manifest(manifest_path) -> report` という純粋な関数であり、
  起動方法（エディタのボタン / Remote Control API / コマンドライン）を知らない（方針 D-1 / 90 §2-1）

### 1.1 設計ルール

| ルール | 内容 |
|---|---|
| 明示性 | 「暗黙の既定値」を UE 側に持たせない。プリセットで解決した**最終値**をマニフェストに書き出す（方針 D-2） |
| 検証可能 | JSON Schema でバリデーションできる。UE 側は読み込み前に必ず検証する |
| 後方互換 | `schemaVersion` を持つ。UE 側は未知のマイナーバージョンを警告付きで受け入れ、メジャー差異は拒否する |
| 追跡可能 | `runId` / `generator` / `source` により「誰がいつ何から書き出したか」が追える |
| 相対パス | `assets[].sourceFile` はマニフェストからの相対パス。`source.dccFile` / `textureFolder` は `assetFolder` からの相対パス。フォルダを移動しても壊れない |
| 記録と指示の分離 | `limits` / `stats` / `coordinateSystem.fbxExportSettings` は UE 側への**指示ではなく記録**。予算監視・再現・リグレッション検知に使う |

## 2. トップレベル構造

```jsonc
{
  "schemaVersion": "0.3.1",
  "runId": "20261010_143000_a1b2c3",
  "preset": "prop",
  "generator":        { /* 3章 */ },
  "coordinateSystem": { /* 4章 */ },
  "source":           { /* 5章 */ },
  "destination":      { /* 6章 */ },
  "material":         { /* 7章 */ },
  "limits":           { /* 8章 */ },
  "validation":       { /* 9章 */ },
  "assets": [ /* 11章・12章・13章 */ ]
}
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `schemaVersion` | ✔ | セマンティックバージョン（`^\d+\.\d+\.\d+$`） |
| `runId` | ✔ | `YYYYMMDD_HHMMSS_<16進6桁>`。実行ログ `%LOCALAPPDATA%/OnePochi/runs/<runId>/` のフォルダ名と一致（90 §2-3） |
| `preset` | | 適用したプリセット名（記録用。値はすでに展開済み）。`null` 可 |
| `generator` | ✔ | 出力元の情報 |
| `coordinateSystem` | ✔ | 座標系・単位の変換記録 |
| `source` | ✔ | アセット元データの所在 |
| `destination` | ✔ | UE 側の出力先ルート |
| `material` | | マテリアル / MI の扱い。省略時は UE 側でマテリアル処理を行わない扱いとする |
| `limits` | | この実行で使ったしきい値の記録 |
| `validation` | ✔ | DCC 側バリデーション結果 |
| `assets` | ✔ | **1件以上**のアセット定義。各要素は StaticMesh / SkeletalMesh / AnimationSequence のいずれか |

> トップレベルおよび全ブロックは `additionalProperties: false`。**未知のフィールドがあるとスキーマ検証で落ちる。**

## 4. coordinateSystem

**事故の最大要因なので必ず記録し、UE 側で検証する。**

```jsonc
"coordinateSystem": {
  "sourceUpAxis": "Z",
  "sourceForwardAxis": "-Y",
  "sourceUnitInMeters": 1.0,
  "targetUpAxis": "Z",
  "targetForwardAxis": "X",
  "appliedScale": 100.0,
  "conversionDoneBy": "fbx_exporter",      // fbx_exporter | tool | none
  "fbxExportSettings": {                   // 自由形式（記録用）
    "global_scale": 1.0,
    "apply_unit_scale": true,
    "axis_forward": "-Y",
    "axis_up": "Z",
    "use_space_transform": true
  }
}
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `sourceUpAxis` / `sourceForwardAxis` | ✔ | DCC 側の軸。`X` / `-X` / `Y` / `-Y` / `Z` / `-Z` |
| `sourceUnitInMeters` | ✔ | DCC の 1単位が何メートルか（> 0） |
| `targetUpAxis` / `targetForwardAxis` | ✔ | UE 側の軸（通常 `Z` / `X`） |
| `appliedScale` | ✔ | DCC 側で既に掛けた倍率（> 0）。`100.0` なら UE 側の Import Uniform Scale は `1.0` にする |
| `conversionDoneBy` | ✔ | `fbx_exporter`（エクスポータ設定に委ねた） / `tool`（ツールが行列変換した） / `none` |
| `fbxExportSettings` | | 実際に使った FBX エクスポータ設定の記録。**自由形式**（`additionalProperties: true`）。再現性のためで、UE 側はこれを設定として読まない |

UE 側はこの値と実際のインポート設定が矛盾する場合、**インポートを中断する**。

## 5. source

アセット元データの所在。**ExchangeRoot（中継置き場）方式は v0.2.0 で廃止**し、
FBX とマニフェストはアセットフォルダの `fbx/` に置く（90 §2-3）。

```jsonc
"source": {
  "assetName": "Crate_01",                                  // 先頭英字・A-Za-z0-9_ のみ
  "assetFolder": "C:/Users/user/Documents/_STUDY/BlenderToUnreal/assets/Crate_01",
  "dccFile": "Crate_01.blend",                               // assetFolder からの相対パス
  "textureFolder": "textures"                                // assetFolder からの相対パス（既定 textures）
}
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `assetName` | ✔ | アセット名。`dccName` 制約（`^[A-Za-z][A-Za-z0-9_]*$`）。アセットフォルダ名と一致させる |
| `assetFolder` | ✔ | アセットフォルダの**絶対パス** |
| `dccFile` | ✔ | 元データ（`.blend`）の `assetFolder` からの相対パス |
| `textureFolder` | | UE に持っていくテクスチャの置き場。`assetFolder` からの相対パス（既定 `textures`）。`null` 可 |

### 5.1 フォルダ構成とパス解決

```
<AssetsRoot>/
└── Crate_01/                      ← assetFolder（フォルダ名 = assetName。先頭数字禁止）
    ├── Crate_01.blend             ← source.dccFile
    ├── onepochi_asset.json        ← 人間が書く設定（UE インポート先・プリセット等）
    ├── fbx/
    │   ├── SM_Crate_01.fbx        ← assets[].sourceFile（マニフェストからの相対パス）
    │   ├── SM_Crate_01_LOD1.fbx   ← lod.levels[].sourceFile
    │   └── onepochi.json          ← ★ このマニフェスト（ツールが生成）
    ├── textures/                  ← source.textureFolder
    ├── substance/                 ← 作業データ（UE には持っていかない）
    └── houdini/                   ← 作業データ（UE には持っていかない）
```

| パスの種類 | 基準 |
|---|---|
| `source.dccFile` / `source.textureFolder` | `source.assetFolder` |
| `assets[].sourceFile` / `lod.levels[].sourceFile` | **マニフェストファイル自身**（= `fbx/`） |
| `materialSlots[].textures` の値 | `source.textureFolder` |

> `AssetsRoot` の実際の場所は未確定（→ 90 §3 の R-1。仮置き `…/BlenderToUnreal/assets/`）。

## 6. destination

```jsonc
"destination": {
  "contentRoot": "/Game/_Dev",
  "environment": "dev",                        // ★ v0.3.0 で追加（dev | production）
  "defaultPath": "/Game/_Dev/Props/Crate_01",
  "allowOverwrite": true,
  "pathWhitelist": ["/Game/_Dev"]
}
```

| フィールド | 必須 | 既定 | 説明 |
|---|---|---|---|
| `contentRoot` | ✔ | — | UE のコンテンツルート（`uePackagePath` 制約）。**`environment` から決まる** |
| `environment` | | `dev` | **書き出し時に選択されていた出力環境**（`dev` / `production` の enum）。記録用。UE 側はこれをレポートに残せる |
| `defaultPath` | ✔ | — | `assets[].destinationPath` を省略できない代わりの既定値・基準（`uePackagePath` 制約）。`material.instancePath` が `null` のときは `<defaultPath>/Materials` が使われる |
| `allowOverwrite` | | `true` | `false` のとき、既存アセットがあればエラーで中断する（誤上書き防止） |
| `pathWhitelist` | | — | **この配下以外への書き込みを UE 側が拒否する（事故防止）。**空配列なら制限なし。**`environment` から決まる** |

### 6.1 pathWhitelist の意図

検証中の誤爆を防ぐための安全弁。`/Game/_Dev` のみを許可しておけば、
`assets[].destinationPath` に本番パスが紛れ込んでも UE 側が書き込みを拒否する。

### 6.2 environment（v0.3.0 で追加 / R-2 の解決）

`contentRoot` と `pathWhitelist` は**プリセットの `destination.environments` から展開された結果**であり、
マニフェストにはすでに展開済みの最終値が入る（§1.1 の「明示性」）。
`environment` はその**どちらの環境を選んだかの記録**である。

| 値 | `contentRoot` | `pathWhitelist` |
|---|---|---|
| **`dev`（既定）** | `/Game/_Dev` | `["/Game/_Dev"]` |
| `production` | `/Game` | `["/Game"]` |

- **既定は `dev`。**明示的に `production` を選ばない限り本番には書かない（フェイルセーフ）
- 選択経路と切り替え方法は [02 §10.4](02_仕様書.md)。未定義の環境名はルール **V-105** のエラーになる
- `pathWhitelist` の検証そのものは v0.2.0 から変わっていない（UE 側が配下でない書き込みを拒否する）

## 7. material

マテリアル / MI の扱い（Q-19 / 90 §2-5）。

```jsonc
"material": {
  "mode": "createInstances",                       // none | assignExisting | createInstances
  "masterMaterialPath": "/Game/_Dev/Materials/M_OnePochi_Base",   // createInstances のとき必須
  "instancePath": null,                            // null なら destination.defaultPath/Materials
  "importTextures": true,
  "textureParameterMap": {                         // テクスチャサフィックス -> MI のパラメータ名
    "_BC":  "BaseColor",
    "_N":   "Normal",
    "_ORM": "ORM",
    "_E":   "Emissive"
  }
}
```

| フィールド | 必須 | 既定 | 説明 |
|---|---|---|---|
| `mode` | ✔ | — | 下表参照 |
| `masterMaterialPath` | `mode=createInstances` のとき ✔ | — | MI の元になるマスターマテリアル。**Blender の UI でユーザーが指定できる**（Q-19）。`null` 可（ただし `createInstances` では非空文字列が必須） |
| `instancePath` | | `null` | MI の出力先。`null` なら `destination.defaultPath` + `/Materials` |
| `importTextures` | | `false` | テクスチャを UE に取り込むか |
| `textureParameterMap` | | — | テクスチャサフィックス → MI のパラメータ名の対応表。キー・値ともに文字列の自由なマップ。サフィックスの定義は 04 §3 |

### 7.1 mode の意味

| `mode` | 挙動 |
|---|---|
| `none` | マテリアルの生成も割当もしない（メッシュのみ取り込む） |
| `assignExisting` | **同名の既存マテリアルを割当**。生成はしない |
| `createInstances` | **マスターから MI を生成して割当**。`masterMaterialPath` 必須 |

### 7.2 MI の命名

Blender のマテリアル名から MI 名を導出する（04 §2.6）。

| Blender マテリアル名 | 判定 | 生成される MI |
|---|---|---|
| `M_Crate_Body` | OK | `MI_Crate_Body` |
| `M_Crate_Metal_01` | OK | `MI_Crate_Metal_01` |
| `Material` / `Material.001` | **エラー**（`M_` プレフィックスなし / `.` 禁止） | — |

**マテリアル名が `M_<名前>` 形式でない場合は書き出し時にエラーにして止める**（Q-19）。
これはスキーマ上も `materialSlots[].slotName` の pattern で強制される（→ 10.1）。

> マスターマテリアル `M_OnePochi_Base`（BaseColor / Normal / ORM / Emissive の最小構成）は
> 仮のものをツール側で用意する（90 §2-5）。**要検証**: UE 5.8 での MI 生成 API（`MaterialInstanceConstant` の
> パラメータ設定）の Python からの到達範囲。

この実行で使ったしきい値の**記録**。**上限超過はエラーではなく警告であり、書き出しを中断しない**（Q-06 / 90 §2-4）。

## 10. 共通部品

複数のアセット種別から参照される定義。

### 10.1 命名・パスの制約

| 定義名 | pattern | 適用先 |
|---|---|---|
| `uePackagePath` | `^/[A-Za-z_][A-Za-z0-9_]*(/[A-Za-z_][A-Za-z0-9_]*)*$` | `destination.contentRoot` / `defaultPath` / `pathWhitelist[]` / `assets[].destinationPath` |
| `ueAssetName` | `^[A-Za-z][A-Za-z0-9_]*$`（1〜128文字） | `assets[].name` / `sockets[].name` |
| `dccName` | `^[A-Za-z][A-Za-z0-9_]*$` | `source.assetName` |
| `materialName` | `^M_[A-Za-z][A-Za-z0-9_]*$` | `materialSlots[].slotName` |

- **先頭は英字**（`uePackagePath` の各セグメントは英字または `_`）。**数字・記号で始められない**（Q-10 / 04 §0 N-1）
- 使用可能文字は `A-Za-z0-9_` のみ。日本語・空白・ハイフン・ドットは不可（04 §0 N-2, N-3）
- マテリアル名のみ `M_` プレフィックスが pattern で強制される（Q-19）

> 一方、`material.masterMaterialPath` / `material.instancePath` / `materialSlots[].ueMaterialPath` /
> `skeleton.assetPath` / `animationSequence.skeletonAssetPath` は**パターン制約のない文字列**。
> スキーマでは検証されないため、値の妥当性は UE 側で確認する。

### 10.2 vec3

長さ 3 の数値配列。`[x, y, z]`。

```jsonc
  "override": ["nanite"]          // preserveSettings でも強制上書きする項目
```

|---|---|---|---|
| `mode` | ✔ | — | `preserveSettings`（UE 側で手修正した設定を残す） / `overwriteAll`（マニフェストの値で全上書き） |
| `override` | | `[]` | `preserveSettings` でも強制上書きする項目。`nanite` / `lod` / `collision` / `lightmap` / `materials` / `sockets` / `buildSettings` |

StaticMesh / SkeletalMesh / AnimationSequence の 3種すべてで任意に指定できる。

#### 10.4.1 `textures` の出力規則（R-4 / 2026-10-13 追加）

**`textures` は DCC（Blender）側が自動で埋めます。**人が書く項目ではありません。
発見規則そのものは [docs/04 §3.1](04_命名規約.md) が正で、ここでは
**マニフェストに何がどう入るか**だけを決めます。

| 項目 | 規則 |
|---|---|
| キー | docs/04 §3 のサフィックス（`_BC` `_D` `_N` `_ORM` `_M` `_R` `_AO` `_E` `_MSK`）。**表の順に並ぶ** |
| 値 | `source.textureFolder` **直下**のファイル名（走査は直下のみ / **再帰しない**） |
| 見つからなかったサフィックス | **キーごと出さない。**空文字やダミーは入れない |
| 1 枚も見つからなかったスロット | **`textures` キー自体を出さない**（`{}` も出さない） |
| 重複 | 1 枚だけ採用し、採用しなかったものは `V-111`（警告）に出す。**マニフェストには採用した 1 枚だけ**が入る |
| `material.importTextures` が false のとき | **それでも出力する。**発見は DCC 側の事実であり、取り込むかどうかは UE 側の方針（方針 D-3 / D-5） |

```jsonc
// S-11（11_static_texture）の実測値（2026-10-13 / Blender 5.2.2 headless）
"materialSlots": [
  {
    "index": 0,
    "slotName": "M_Crate_Body",
```

> 上記の出力はそのまま検証を通ります（`tools/validate_manifest.py` で実測）。

### 10.5 sockets[]

```jsonc
"sockets": [
  {
    "name": "weapon_r",
    "parentBone": "hand_r",       // Static Mesh では null
    "location": [0, 0, 0],        // UE 座標系・cm 単位の最終値
    "rotation": [0, 0, 0],        // オイラー角（度）, UE 座標系
    "scale": [1, 1, 1]
  }
]
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `name` | ✔ | ソケット名（`ueAssetName` 制約）。Blender 側は `SOCKET_<名前>` の Empty（04 §2.4）。**違反は V-050 で書き出し前に止まる** |
| `parentBone` | | 親ボーン名。Skeletal Mesh で使う。`null` 可 |
| `location` | ✔ | **UE 座標系・cm 単位の最終値**（DCC 側で変換済み） |
| `rotation` | ✔ | オイラー角（度）、UE 座標系。**`[roll, pitch, yaw]` = `[X 回転, Y 回転, Z 回転]`** の順。UE 側は `unreal.Rotator(roll, pitch, yaw)` にこの順で渡す（コンストラクタの引数順が `(roll, pitch, yaw)` であることを実機で確認済み） |
| `scale` | ✔ | スケール |

#### 実測（S-08 / UE 5.8.3 / 2026-10-11）

Blender の `SOCKET_Lid`（ローカル位置 `(0, 0, 1.0)` m / 回転 `(13.7897, 15.6831, -20.228)` 度）が
UE で次のとおりになりました。**宣言値と実測の差分は 0**です。

| 項目 | マニフェストの宣言値 | UE の実測値 |
|---|---|---|
| `location` | `(0, 0, 100)` | `(0, 0, 100)` |
| `rotation` | `(-13.7897, 15.6831, 20.228)` | `(-13.7897, 15.6831, 20.228)` |
| `scale` | `(1, 1, 1)` | `(1, 1, 1)` |

変換規則は**基底変換の共役** `R_ue = B · R_bl · B⁻¹`（`B = diag(1, -1, 1)`）です。
XYZ オイラー角では `(a, b, c) → (-a, b, -c)` になり、
検証済みの点の対応（`(x, y, z) → (x, -y, z)`）と整合します。

> **残っている不確かさ**: 「どの軸で左右手系の反転を吸収するか」は**規約の選択**で、
> 数値の一致だけでは決まりません。UE でソケットに何かを付けて目視するまで
> 「要検証」を外していません（→ [13 P4](13_ロードマップ.md) / A-11）。

> **UE 側の実装メモ**: Interchange は FBX の `SOCKET_` 命名から**ソケットを自前で作る**ため、
> ポストプロセスで追加すると**同名が2個**になります。インポータ製は
> **scale に 100 倍が混入し、roll に -90° が残ります**（実測）。
> 本ツールは**インポータ製を消して上記の宣言値で作り直します**
> （→ [99 P-17](99_作業ルール.md)）。

### 11.4 staticMesh.lod（コレクション方式）

**v0.2.0 の変更点。**オブジェクト名の `_LOD0` サフィックス方式は廃止し、Blender のコレクションで LOD を表す
（Q-11 / 04 §2.2）。**LOD ごとに別 FBX を出力する**ため、`levels[].sourceFile` が必須になった。

```
Crate_01/                 ← アセット用コレクション（名前 = アセット名）
├── LOD0/                 ← 必須。欠番不可。オブジェクト名に _LOD は付けない
│   └── Crate_01
├── LOD1/
│   └── Crate_01
├── Collision/
│   ├── UCX_Crate_01_01
│   └── UBX_Crate_01_01
└── Sockets/
    └── SOCKET_Lid
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `mode` | ✔ | `none`（LOD なし） / `auto`（UE 側で自動生成） / `manual`（コレクションから取得） |
| `autoLodCount` | | `mode=auto` のとき生成する LOD 数（1〜8） |
| `levels[]` | | `mode=manual` で使う LOD の配列 |
| `levels[].level` | ✔ | LOD レベル（整数 ≧ 0）。`LOD0` 必須・欠番はエラー |
| `levels[].sourceFile` | ✔ | **この LOD の FBX。マニフェストからの相対パス** |
| `levels[].sourceCollection` | | Blender 側のコレクション名（例 `LOD1`）。`null` 可 |
| `levels[].sourceNode` | | FBX 内のノード名。`null` 可 |
| `levels[].screenSize` | | 画面占有率のしきい値（0〜2）。`null` 可（UE 側の既定に任せる） |
| `levels[].triangleCount` | | **（v0.3.1 で追加 / 省略可）**この段の三角形数（整数 ≧ 0）→ 下記 |

#### levels[].triangleCount（v0.3.1 / R-6）

DCC 側が数えた**この LOD 段の三角形数**。`null` は許さない
（**値が取れなかった段はキーごと出さない**。`0` を入れると「三角形が 0 枚」という
別の主張になってしまう）。

| | 宣言がある（v0.3.1 以降） | 宣言が無い（v0.3.0 以前 / 数えられなかった） |
|---|---|---|
| UE 側の検証 | `comparison.lodTriangleCounts` で**実測値と厳密比較**する | 項目を作らず、**降順チェックにフォールバック**する |
| 落ちる条件 | 1段でも値が違う / 段数が違う | `comparison.lodTriangleCountsDescending`: 段が進んでも三角形数が減っていない |

- 出所: Blender 側は `collect.lod_triangle_count()`
  （評価後メッシュの `loop_triangles`）。**バリデータ V-047 と `stats.triangleCount` と
  同じ数え方**にしてある。食い違うと UE 側が厳密比較で赤くなる
- UE 側: `onepochi_ue/lod.py` の `declared_lod_triangle_counts()` / `compare_lod()`。
  `levels[]` に LOD0 が無い場合は `stats.triangleCount` を LOD0 として補う
- `levels[]` は**2段以上あるときだけ**出力される（`mode` が `manual` に切り替わるとき）。
  LOD の無いアセットには `levels` ごと存在しないので、`triangleCount` も現れない

プリセットごとの既定（90 §2-2）:

| プリセット | Nanite | LOD |

### 12.4 compatibilityMode（v0.2.0 で追加）

Skeleton 流用時の階層互換判定モード。**完全一致とサブセット許容の両方を選べるようにした**（Q-09）。

| 値 | 判定 | 想定する使い方 |
|---|---|---|
| `exact` | ボーン階層の**完全一致**を要求 | **量産時。**意図しない Skeleton のズレを確実に弾く |
| `subset` | 既存 Skeleton の**部分集合**なら許可 | **試行錯誤時。**ボーンを削った試作メッシュを既存 Skeleton に載せたいとき |

既定は `exact`（安全側）。不一致の場合、UE 側は**インポート前に中断**する。

判定ロジックは `tools/ue_plugin/onepochi_ue/skeleton_compat.py:compare()` に**実装済み**
（`unreal` 非依存 / 単体テスト 35 件）。`subset` でも**親子関係の一致は必須**で、
名前が揃っていても親が違えばバインドが破綻するため不許可にする（[02 §6.3](02_仕様書.md)）。

> **未実装**: **実際の Skeleton アセットから階層を読み取って `compare()` に渡す経路**と、
> Interchange への既存 Skeleton の指定（[02 §6.8](02_仕様書.md)）。

### 12.5 boneHierarchy / boneHierarchyHash（v0.2.0 で追加）

`compatibilityMode` の判定根拠を、ハッシュだけでなく**元データとしても持たせる**ようにした。

```jsonc
"boneHierarchy": [
  [null,     "root"],      // [親ボーン名 or null, ボーン名]
  ["root",   "pelvis"],
  ["pelvis", "spine_01"]
]
```

| 項目 | 内容 |
|---|---|
| 形式 | 長さ 2 の配列（`[親ボーン名 or null, ボーン名]`）を**階層順**に並べたもの。要素は文字列または `null` |
| ルート | 親が存在しないボーンは第1要素が `null` |
| `boneHierarchyHash` | 下記の算出規則による `sha1:<hex>` |
| トランスフォーム | **ハッシュに含めない**（階層構造の同一性のみを見る） |
| `exact` 判定 | UE 側が既存 Skeleton から同じ方法でハッシュを算出し、不一致なら中断 |
| `subset` 判定 | ハッシュ比較ではなく `boneHierarchy` のペア集合が既存 Skeleton の部分集合かを見る |

#### ハッシュ算出規則（v0.3.0 で確定）

```
各ペアを  "<親ボーン名>><ボーン名>"  の文字列にする（親が null / 空なら親の部分は空文字）
  例: [null, "root"]      -> ">root"
      ["root", "pelvis"]  -> "root>pelvis"
それらを階層順に "\n"（LF）で連結し、UTF-8 でエンコードして SHA-1
先頭に "sha1:" を付ける
```

- 実装は **Blender 側 `core/manifest.py:bone_hierarchy_hash()`** と
  **UE 側 `onepochi_ue/skeleton_compat.py:bone_hierarchy_hash()`** の2箇所にある。
  **両者は同一実装でなければならない**（食い違うと「同じ階層なのに不一致」と誤判定する）
- `tools/dcc_blender/tests/test_core.py::TestCrossPackageHash` が
  **両者が同じ値を返すことを機械的に検証**している。v0.2.0 の「要確定」はこれで解除した

### 12.8 skeleton.bones[]（`$defs/bone` / v0.3.0 で追加）

ボーン1本の詳細。**座標はすべて UE 系（cm）に変換済み**。
DCC 側の予測値であり、UE 側の実測と突き合わせるための材料（§1.1 の「記録と指示の分離」）。

```jsonc
{
  "name": "bone_02",
  "parent": "bone_01",
  "index": 2,
  "useDeform": true,
  "isLeaf": true,
  "lengthCm": 25.0,
  "headCm": [0, 0, 75],
  "tailCm": [0, 0, 100],
  "rotation": [0, 0, 0]
}
```

| フィールド | 必須 | 説明 |
|---|---|---|
| `name` | ✔ | ボーン名（命名規約の対象 / V-066） |
| `parent` | ✔ | 親ボーン名。ルートは `null` |
| `index` | ✔ | 階層順のインデックス（整数 ≧ 0） |
| `useDeform` | | Blender の `bone.use_deform`。`false` のボーンは `use_armature_deform_only` で落ちる |
| `isLeaf` | | **子を持たないボーン** → 下記の警告 |
| `lengthCm` | | ボーン長（cm ≧ 0）。Armature のワールドスケールを反映した値 |
| `headCm` / `tailCm` | | head / tail のワールド位置（UE 座標系・cm） |
| `rotation` | | rest 姿勢のオイラー角（度）。**要検証**（UE 側の実測と突き合わせていない） |

> **⚠ `isLeaf` が `true` のボーンの `lengthCm` は FBX 往復で保存されない。**
> **FBX はボーンを「head→tail の線分」ではなく「関節（ノード）のトランスフォーム」として持つ**ため、
> 子を持たないボーンは tail の位置を表現する手段が無く、インポータが推定する。
> 実測では `0.25 m` が **`0.35 m`** になった（S-04 / Blender 5.2.2 / `add_leaf_bones=False`）。
>
> **したがって `isLeaf` なボーンの `lengthCm` を UE 側の検証項目にしてはいけない。**
> 往復で保存されるのは **ボーン名 / 親子関係 / `headCm`** である。
> 出典: [99 P-11](99_作業ルール.md) / [14 §8.4](14_サンプル指摘.md) / [02 §6.7](02_仕様書.md)。

### 12.9 skeletalMesh.skin（`$defs/skinStats` / v0.3.0 で追加）

スキンウェイトの実測統計。**バリデーション（V-068 / V-069 / V-070 / V-071 / V-072）の根拠**を
マニフェストに残し、UE 側・レポート側から追えるようにする。

| フィールド | 説明 |
|---|---|
| `vertexCount` | 対象メッシュの頂点数 |
| `unassignedVertexCount` | **ウェイトが無い頂点**（UE では原点に吸い寄せられる / **V-068 エラー**） |
| `zeroWeightVertexCount` | ウェイトの合計が実質ゼロの頂点（**V-070 エラー**） |
| `notNormalizedVertexCount` | 合計が 1.0 でない頂点（**V-069 警告**）。**書き出し時に複製側で正規化される**ため、FBX 側では 0 になる |
| `worstWeightTotal` | 最も 1.0 から離れていた合計値。`null` 可 |
| `maxWeightDeviation` | 1.0 からの最大ズレ |
| `maxInfluencesPerVertex` | 1頂点あたりの最大影響ボーン数（上限超過は **V-071 警告**） |
| `bonesWithoutWeight` | ウェイトが1つも割り当たっていないボーン名の配列（**V-072 警告**） |

全フィールド任意。`skeletalMesh.skin` 自体も `null` を許す（スキン情報が取れなかった場合）。

> **この統計は「書き出し前の DCC シーンの状態」である。**
> `notNormalizedVertexCount` が 0 でないマニフェストは「ズレがあったが自動修正して書き出した」
> という記録であり、FBX の中身は正規化済みである（[02 §6.5](02_仕様書.md)）。

### 13.4 現時点の UE 側の挙動

| 状況 | 挙動 |

## 15. バージョニング方針

| 変更 | バージョン | UE 側の挙動 |
|---|---|---|
| フィールド追加（任意） | パッチ / マイナー | 受け入れる |
| フィールドの意味変更・必須化・削除 | メジャー | **拒否**して明示エラー |
| 未知のフィールド | - | スキーマ検証で落ちる（全ブロック `additionalProperties: false`）。UE 側は明示エラーにしてレポートに記録 |

- `0.1.0` → `0.2.0` は**マイナー**だが、`source` ブロックの新規必須化・`materialSlots[].slotName` の
  pattern 追加・`lod.levels[].sourceFile` の必須化を含むため、**v0.1.0 のマニフェストは v0.2.0 として検証できない**。
  `0.x` 系は破壊的変更を許容する期間として扱う（1.0.0 以降は上表どおりに運用する）
- `0.2.0` → `0.3.0` は**追加のみ**（必須化・削除・意味変更なし）。
  **v0.2.0 のマニフェストは v0.3.0 のスキーマで検証できる**
- `0.3.0` → `0.3.1` は**任意フィールド1つの追加のみ**（`lod.levels[].triangleCount`）。
  **v0.3.0 のマニフェストは v0.3.1 のスキーマで検証でき**、UE 側も宣言が無ければ
  従来の降順チェックに落ちる（→ §11.4）
- 本書とスキーマは常に同時に更新する（CLAUDE.md の作業ルール）
- **バージョンをテストに直書きしない。**実装の定数（`manifest.SCHEMA_VERSION` /
  `manifest_io.SUPPORTED_SCHEMA_VERSION`）から導出する（[99 P-14](99_作業ルール.md)）
