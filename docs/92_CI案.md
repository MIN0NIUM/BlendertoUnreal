## 0. 要点（3行）

1. CI に載せられるのは **`python tools/run_tests.py --no-blender` だけ**。
   Blender も UE も GitHub のホストランナーには無い
2. そのとき **全 25 ステップのうち 12 ステップしか動かない**。
   残り 13 ステップ（Blender 結合 8 / UE 実機 5）は skip される。
   **「緑だから安全」ではない**
3. だから CI は **必ず `--list-steps` を先に実行**し、
   「このジョブが何を検証していないか」をログに残す

## 2. 案 A: ホストランナーで `--no-blender` だけを回す（**いますぐ載せられる**）

```yaml
# .github/workflows/tests.yml  （← このファイルは未作成。採用時にコピーする）
name: onepochi-tests

on:
  push:
  pull_request:
  workflow_dispatch:

jobs:
  python-only:
    name: Python のみ（Blender / UE 不要）
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        # **Windows が本番**。ubuntu は「落ちたら直す」程度の補助
        #（→ §2.2 プラットフォーム差の落とし穴）
        os: [windows-latest, ubuntu-latest]

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: 依存をインストール
        # 外部依存は jsonschema だけ。無いと「マニフェストのスキーマ検証」が
        # 終了コード 2 で落ちる（= 気づける。黙って skip されはしない）
        run: python -m pip install --upgrade pip jsonschema

      - name: 何が実行され、何が skip されるかを先に出す（**必須**）
        # ここを省くと「緑なのに何も検証していない」事故に気づけない。
        # このコマンドはテストを1つも実行しない
        run: python tools/run_tests.py --list-steps --no-blender

      - name: テスト
        run: python tools/run_tests.py --no-blender
```

### 2.1 `--list-steps` を必ず入れる理由（**M-8 の本題**）

`run_tests.py` は **見つからないものを黙って skip する**設計です
（Blender が無ければ結合テストを飛ばす / `--with-ue` が無ければ UE を飛ばす）。
これは手元では親切ですが、**CI では「0 ステップしか動いていないのに緑」になりうる**。

`--list-steps` は **何も実行せずに**、全ステップと「実行 / skip（＋理由）」を出します。
ジョブのログに残るので、**後から「このコミットで何が検証されたか」を追える**。

> Blender の有無は実際の検出関数 `find_blender()` で判定します（**存在確認だけ / 起動しない**）。
> UE が応答するかは**見ません**（一覧表示のために UE に触りに行かないため）。

### 2.2 プラットフォーム差の落とし穴（**ubuntu だけでは危ない**）

[docs/99 P-30](99_作業ルール.md) の実例:
`os.path.basename("//textures/T_x.png")` は **Windows では `''`、Linux では `'T_x.png'`**。
Blender の相対パス（`//` 始まり）を Windows の `ntpath` が UNC と解釈するためです。
**この不具合は Linux の CI では永遠に検出できません。**

- → **`windows-latest` を必ず含める**。制作現場の実機も Windows
- → `ubuntu-latest` は「偶然 Windows に依存していた箇所」をあぶり出す補助として足す

> **要検証**: `ubuntu-latest` で 12 ステップが全部通るかは**未確認**です
> （この環境は Windows 11 のみ）。最初の実行で落ちたら、
> まず **matrix から ubuntu を外して windows だけで緑にする**のが先。

## 4. 将来案 B: Blender をセルフホストランナーに置く

案 A の ❌ のうち **8 ステップ（13〜20）を回収できます**。UE はまだ載りません。

```yaml
  blender-integration:
    name: Blender 結合テスト（セルフホスト）
    runs-on: [self-hosted, windows, blender]   # ランナーに付けたラベル
    needs: python-only
    steps:
      - uses: actions/checkout@v4
      - name: 何が実行され、何が skip されるかを先に出す
        run: python tools/run_tests.py --list-steps
      - name: テスト（Blender 結合まで / UE は使わない）
        run: python tools/run_tests.py
        env:
          # 複数バージョンが入っている環境では明示する（docs/99 P-1b）
          BLENDER_EXE: C:\Users\runner\Documents\Blender\stable\blender-5.2.2-lts.d13f752e3b9c\blender.exe
```

**成立条件**

- ランナー機に **Blender 5.2 LTS** が入っていること。`BLENDER_EXE` で場所を固定する
  （自動検出もあるが、複数バージョン同居だと新しい方が選ばれる → [docs/99 P-1b](99_作業ルール.md)）
- **ランナーは Windows にする。**§2.2 のプラットフォーム差があるため
- `samples/blender/*.blend` がリポジトリに入っていること
  （入っていないサンプルは `--list-steps` に
  「サンプルの .blend が見つからない」と理由つきで出る）

**注意点**

- 結合テストは `samples/blender/<名前>/fbx/` に **FBX とマニフェストを書き出します**。
  ワークスペースが汚れるので、ジョブの最後に `git status` を見るか
  `actions/checkout` の `clean: true`（既定）に任せる
- Blender のアドオン有効化で `Exception in module unregister()` のような
  **無関係なアドオンの警告**が出ることがある（終了コードには影響しない / 実測）
- GitHub ホストランナーに Blender を都度インストールする案もあるが、
  **ダウンロード量が大きく毎回数分かかる**ため、継続運用ならセルフホストが素直

## 5. UE を CI に載せない理由

**結論: 載せません。**手元の `--with-ue --via-rc` を正とします。

| # | 理由 | 具体 |
|---|---|---|
| 1 | **ライセンス / 配布** | UE エディタは GitHub のホストランナーに入っていない。自前で入れるには EULA への同意と Epic アカウントの認証が要る。CI 用に自動で同意させる構成は作らない |
| 2 | **容量とビルド時間** | エンジン本体だけで数十 GB。加えて DDC（Derived Data Cache）が無い状態では初回取り込みにさらに時間がかかる。PR ごとに回す規模ではない |
| 3 | **単一インスタンス制約** | 本番経路は**起動中のエディタに Remote Control で依頼する**（`--via-rc`）。エディタは 1 プロジェクト 1 インスタンスで、**同時実行できない**（[docs/99 P-16](99_作業ルール.md) / P-20）。CI の並列ジョブとは根本的に相性が悪い |
| 4 | **終了コードが信用できない** | 取り込みが成功していても `UnrealEditor-Cmd.exe` が **1 を返す**（[docs/99 P-7](99_作業ルール.md)）。CI の成否判定に使えず、レポート JSON を読む専用の判定層が別途必要になる |
| 5 | **commandlet では取れない情報がある** | `StaticMeshEditorSubsystem` が `None` を返すなど、headless と GUI で挙動が違う（[docs/99 P-5](99_作業ルール.md)）。**CI が緑でも GUI で壊れている**ことがありうる |

**代わりにやること**

- UE 実機の検証は **リリース前チェックリスト**に置く（手元で `--with-ue --via-rc`）
- UE 側ロジックは **`unreal` をフェイク化した単体テスト**で CI に載せる
  （ステップ 5〜8。これは既に案 A に入っている）
- 実機で分かった事実は **[docs/99](99_作業ルール.md) に落とす**。CI の代わりに知識で守る
