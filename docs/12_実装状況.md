> **`core/verify.py` を分けた理由**: 「どの比較項目の一致を要求するか」は
> 往復テストとボタン経路の結合テストの**両方**が必要とする。2か所に書くと必ずずれるので、
> bpy にも unreal にも依存しない場所に1つだけ置いた。`vertexCount` のように
> **FBX の往復で必ず増える**項目（S-01: 13 → 40 / S-04: 96 → 216）を
> 必須にしない判断もここに書いてある。

> **`test_validate.py` が bpy 無しで動く仕組み**: `validate.py` は `import bpy` するが
> **モジュール読み込み時には bpy を使っていない**（実際に触るのは `bpy.data.objects` /
> `bpy.data.collections` / `bpy.data.materials` / `bpy.context.scene` の4か所だけ）。
> テスト側で `sys.modules` に最小のスタブを差し込み、検査対象には
> **ダックタイピングの疑似オブジェクト**を渡している。850 行超で最大のファイルなのに
> 回帰検知が無かった状態を解消した。

> **`test_integration_onepochi_button.py` が必要な理由**: `run_headless.py --mode export` は
> `pipeline.export_asset()` を直接呼ぶため、**UE への依頼（`ui._send_to_ue`）を通らない**。
> P2 の DoD は「ボタン1回で UE にアセットが生成される」なので、
> オペレータ `bpy.ops.onepochi.export()` を実際に実行しないと検証したことにならない。

> **`addons/` が必須な理由（実測 / R-3 の解決）**: Blender は **Script Directory 配下の `addons/` しか
> アドオンとして探さない**。`tools/dcc_blender` を Script Directory に登録した状態で
> `bpy.utils.script_paths(subdir="addons")` が **`[]`** を返し、アドオンが発見されなかった。
> `addons/onepochi/` に移動したあとは `addon_utils.modules()` が `onepochi` を発見し、
> `addon_utils.enable("onepochi")` が成功し、`Scene.onepochi` と
> `onepochi.{validate,export,send_to_ue,check_ue,select_target,open_output,guess_name}` が登録される。
>
> **ユーザー作業が必要**: 実測時点で `preferences.filepaths.script_directories` が**空**だった
> （登録が保存されていない）。**Preferences で `tools/dcc_blender` を Script Directory に再登録し、
> プリファレンスを保存**してください（→ §6.2 A-6）。

> **`onepochi_ue/skeletal.py` の Python プロパティ名は「導出値」であって実測値ではない。**
> この環境には UE の Python スタブ（`Intermediate/PythonStub/unreal.py`）が生成されて
> いないため、エンジンのヘッダと `PyGenUtil.cpp` の命名規則から手で導いている。
> そのため**すべての設定で候補名を順に試す**構えにしてある
> （`set_editor_property()` は Python 名が解決できないと生の C++ FName に
> フォールバックするため、`("import_skeletal_meshes", "bImportSkeletalMeshes")` の
> どちらでも通る）。確定させるには `probe_skeletal_api.py` を実行する
> （→ [docs/99](99_作業ルール.md) P-15）。

> **`onepochi_rc.py` は「薄い受け口」に徹する。**取り込みの本体は `onepochi_ue.importer` にあり、
> 起動方法（commandlet / Remote Control / UE のコンソール）に依存しない（方針 D-1）。
> **例外を外に投げず、失敗しても必ずレポート JSON を書く**（docs/99 P-6 / P-7 の教訓）。

> **`skeleton_compat.py` は `unreal` を import していない。**UE を起動せずに互換判定をテストできる
> （`manifest_io.py` と同じ方針）。UE から読み取ったボーン階層を引数で受け取る設計。

> `run_import.py` はジョブファイルを **3箇所の順に探索**し、**探索結果を必ずログに出す**:
> ① スクリプト隣の `job.json` → ② `%LOCALAPPDATA%/OnePochi/job.json` → ③ `<UEプロジェクト>/Saved/onepochi_job.json`

### 2.5 E2E 往復テスト（Blender → FBX → UE）

**Blender の書き出し → UE headless インポート → `comparison` 検査**までを1コマンドで通します。

```bash
#   --keep         中間生成物（FBX / マニフェスト / レポート）を残す
#   --skip-export  既存の FBX + マニフェストを使い、UE インポートだけやり直す
```

対象サンプル（`SAMPLES`）: **01 / 02 / 03 / 04 / 05 / 06 / 08 の 7 件**。
**07_static_lod だけは未登録**です（サンプル側の要修正 → [14 §9.3](14_サンプル指摘.md)）。

#### `--via-rc`（Remote Control 経路）

`UnrealEditor-Cmd.exe` を起動せず、**起動中の UE エディタ**に取り込みを依頼します。
経路は Blender の「ワンポチ」ボタンと**完全に同じ**（`core/ue_bridge.py` を共有）なので、
**本番経路の回帰テストとしても機能します**。

| 項目 | `--via-rc` あり | なし（既定） |
|---|---|---|
| UE の起動状態 | **起動したまま**（必須） | **閉じておく**（commandlet が別インスタンスを開くため） |
| 検証用アセットの削除 | `EditorAssetLibrary.delete_directory()`（UE 自身に消させる） | `shutil.rmtree(Content/_Dev)` |
| UE 側モジュールの再読み込み | `sys.modules` から `onepochi_rc` / `onepochi_ue*` を外す | プロセスごと新規 |
| 所要時間 | **短い**（UE の起動待ちがない） | 長い |

> **エディタが開いている間に `Content/` をファイルシステムから消してはいけません**
> （メモリ上のパッケージと食い違う / X-6）。`--via-rc` では UE 自身に消させています。
>
> **UE エディタは起動したままなので、コードを直しても古いモジュールが使われます。**
> `importlib.reload` は `onepochi_rc` にしか効かない（`onepochi_ue` は `handle()` の中で
> import される）ため、`--via-rc` は実行前に `sys.modules` から外しています。

#### commandlet 経路（既定）

UE は headless で起動します。

```
C:\Program Files\Epic Games\UE_5.8\Engine\Binaries\Win64\UnrealEditor-Cmd.exe
  <uproject> -run=pythonscript -script="<path>" -unattended -nopause -nosplash -stdout
```

> **UE の終了コードは成否判定に使えません。**空プロジェクトでも GameFeatureData の既知エラーで `1` を返します。
> 判定は**必ずレポート JSON**（`ue_report.json` の `comparison`）で行ってください（→ §7）。

> サンプル3つは**いずれもオブジェクト名が `Crate_01`** です。UE の出力先を
> `S01_Minimal` / `S02_Collision` / `S03_Multislot` に分けないと同じアセットへ上書きされ、
> **コリジョンが累積して計測が壊れます**（実際に一度踏みました → §7）。

### 2.6 真のワンポチ（Remote Control API 経由）— ✅ 成功経路まで実機検証済み

Blender の「UE へ取り込む」ボタン（または書き出し後の自動依頼）で、
**起動中の UE エディタ**に取り込みを実行させます。実装は
`core/ue_bridge.py`（Blender 側）と `onepochi_rc.py`（UE 側）。

```
Blender: onepochi.json を書く
      → HTTP PUT http://127.0.0.1:30010/remote/object/call
           objectPath   = /Script/PythonScriptPlugin.Default__PythonScriptLibrary
           functionName = ExecutePythonCommandEx
           executionMode = ExecuteStatement
UE:   onepochi_rc.handle(manifest, report, dry_run, allow_failed)
      → onepochi_ue.importer.import_from_manifest()
      → ue_report.json を書く
Blender: ue_report.json を読んでパネルに表示
```

| 設定 | 既定 | 置き場 |
|---|---|---|
| `ue.remoteControlUrl` | `http://127.0.0.1:30010` | `tools/presets/project_default.json` |
| `ue.timeoutSeconds` | `180` | 同上 |
| `ue.autoImport` | `false` | 同上（UI のチェックボックスで上書き） |

> HTTP は「依頼が届いたか」だけを見て、**レポートが無ければ失敗扱い**にします。
> 依頼の前に前回のレポートを削除し、古い結果を成功と誤認しないようにしています。

| 項目 | 結果 |
|---|---|
| 関数呼び出し | **HTTP 400 で拒否された**: `Object Default__PythonScriptLibrary cannot be accessed remotely, check remote control project settings.` |

#### 必要な設定 — ✅ **`Config/DefaultRemoteControl.ini` に固定済み**（2026-10-13 / R-5）

**Project Settings の UI からは入れません。**UI で入れた値は
`Saved/Config/WindowsEditor/RemoteControl.ini`（ユーザー単位）に書かれ、
**エディタを再起動すると失われることが実測で分かりました**（[docs/99 P-29](99_作業ルール.md)）。
チーム配布でも同じ事故が起きるため、**プロジェクト側の `.ini` に固定**しています。

置き場所は **`UEProject/OnePochiPlayground/Config/DefaultRemoteControl.ini`**、
セクション `[/Script/RemoteControlCommon.RemoteControlSettings]`。

> **`DefaultEngine.ini` に書いても完全に無視されます。**`URemoteControlSettings` は
> `UCLASS(config = RemoteControl)` で宣言されているため（`RemoteControlSettings.h:180`）、
> 設定は `RemoteControl.ini` 階層からしか読まれません。2026-10-13 に実測で確認しました。

```ini
[/Script/RemoteControlCommon.RemoteControlSettings]
bEnableRemotePythonExecution=True
bRestrictServerAccess=True
bAllowAnyRemoteFunctionCall=False
bAllowConsoleCommandRemoteExecution=False
bSecuritySettingsReviewed=True
+CustomAllowedRemoteFunctionCalls=(ClassPath="/Script/PythonScriptPlugin.PythonScriptLibrary",FunctionName=("ExecutePythonCommandEx"),bAllowChildClasses=False)
```

| 設定 | なぜ必要か（エンジンソースで裏取り済み） |
|---|---|
| `bEnableRemotePythonExecution=True` | **本命。**これが false のときだけ `PythonScriptLibrary` が**オブジェクト単位で**拒否される（`RemoteControlModule.cpp:2563 CanBeAccessedRemotely`）。ここが見ている唯一の条件 |
| `+CustomAllowedRemoteFunctionCalls=...` | `ExecutePythonCommandEx` は既定の `AllowedRemoteFunctionCalls` に**入っていない**（`RemoteControlSettings.cpp:25`）ので名指しの許可が必須。**先頭の `+` が要る**（配列プロパティ） |
| `bRestrictServerAccess=True` | **緩めない側。**`127.0.0.1` はクライアント許可リストの判定対象外として常に通る（`RemoteControlDefaultPreprocessors.cpp:419`）ので、True のままで支障がない |
| `bAllowAnyRemoteFunctionCall=False` | True にすると何でも呼べてしまう。**許可は `ExecutePythonCommandEx` の 1 件だけ**に絞る |
| `bAllowConsoleCommandRemoteExecution=False` | コンソールコマンドの遠隔実行は不要 |
| `bSecuritySettingsReviewed=True` | エディタ側の警告表示用フラグ。**実行時のゲートからは参照されていない**（UE 5.8 の公開ソースを全文検索して確認）ので拒否の原因にはならない |

> **`Saved/Config/WindowsEditor/RemoteControl.ini` は後から読まれるので後勝ち**です。
> そちらに違う値が残っていると `Config/DefaultRemoteControl.ini` を打ち消します。
> `python tools/check_rc_config.py` が両方を読み、打ち消しが起きていたら警告します
> （**UE を起動していなくても動きます**。`--ini-only` で設定ファイルの点検だけもできます）。

#### 失敗の切り分け（`ue_bridge.classify_failure()`）

UE のエラー文から原因を特定し、**日本語で対処手順まで**返します（Q-18）。
対応しているのは **Python 実行が無効 / 許可リスト未設定 / 404（プラグイン無効） /
接続拒否（UE 未起動） / タイムアウト** の 5 パターンです。

**`stats.triangleCount` と V-047 と同じ値**（評価後メッシュの `loop_triangles`）になるようにしました。
同じ「三角形数」が場所によって違う値になるのが一番たちが悪いためです。

#### 落とし穴: **数えるのは `prepare.prepare()` の前**

`prepare()` の実行中は、元オブジェクトが `__onepochi_orig__*` に退避され、
**元の名前は複製（モディファイア適用済み）が持っています**（→ [99 P-0](99_作業ルール.md)）。
この状態で名前を使って引くと**複製側の三角形数**が返り、値がずれます。
そのため **`prepare()` に入る前に元オブジェクトから数えます**。

## 5. 設計上の判断（実装して分かったこと）

| # | 判断 | 理由 |
|---|---|---|
| I-1 | FBX 設定は**実オペレータのプロパティと照合してフィルタする** | Blender のバージョンで引数が増減する。未知の引数は黙って捨てず**警告として記録**し、推測で動かさない |
| I-2 | トランスフォームの焼き込みは**オペレータを使わず行列計算で行う** | `bpy.ops.object.transform_apply` はコンテキスト依存。headless で安定させるため `mesh.transform()` + `matrix_basis` を直接操作 |
| I-3 | 三角形化は **bmesh** で行う | 同上。モディファイア追加→適用よりも副作用が少なく、統計値も正確になる |
| I-4 | LOD は **LOD ごとに別 FBX** を書き出す | FBX の LOD グループ規約（`LOD_<name>` ノード）に依存すると UE 側の解釈に引きずられる。別ファイルなら確実 |
| I-5 | UE 側は**全ての API 呼び出しを個別に try で囲む** | UE 5.8 の API は未検証部分が多い。1つ無くても完走させ、失敗はレポートに残す |
| I-6 | UE 側インポートは `options=None` にして Interchange 既定パイプラインに任せる | パイプラインの Python API（`override_pipelines`）は扱いが難しく、設定はポストプロセスで十分（方針 D-6） |
| I-7 | マニフェストの `stats` に **DCC 側の予測値**を入れ、UE 側で実測と突き合わせる | 座標系・単位の事故を**機械的に検出**できる。`comparison` ブロックがその結果 |
| I-8 | **宣言した状態をポストプロセスで強制する**（自動生成コリジョンの削除） | Interchange はコリジョン無しの FBX に凸を1個**勝手に作る**（C-7）。マニフェストが `collision.simple = "none"` と宣言しているなら、`agg_geom` の各配列を空にして**宣言どおりの状態にする**。インポータの気分に結果を左右させない（方針 D-6 の実践例） |
| I-9 | **生成物の特定は `InterchangeManager.import_asset()` の戻り値で行う** | `AssetImportTask` 経由では Interchange が非同期に走り `imported_object_paths` が空になる（C-2）。保存前のパッケージはアセットレジストリに載らないので `list_assets` の差分でも拾えない。`import_asset()` は**同期で参照文字列の配列を返す**（C-1）ので、これが唯一確実 |
| I-10 | **Remote Control の結果は `ue_report.json` で判定し、HTTP レスポンスの形に依存しない** | レスポンス構造は UE のバージョンで変わりうる（docs/99 P-6 / P-7）。HTTP は「依頼が届いたか」だけに使い、レポートが無ければ失敗扱いにする。ログ行の抽出は**取れなくても失敗にしない**診断の補助に留める |
| I-11 | **UE へ送る Python は1行（セミコロン区切り）に収め、分岐を入れない** | `if` などの複合文は実行モードによって解釈が変わる。`importlib.reload` を毎回入れて、UE を再起動せずにコード変更を反映できるようにしている |
| I-12 | **ウェイトの正規化のズレはエラーにせず、複製側で直す** | しきい値 0.01 でエラーにすると**ユーザーが修正済みのサンプル2件が両方書き出せなくなる**（実測）。手付けウェイトでは 1〜2% のズレが普通に出て、UE も取り込み時に正規化する。実害があるのは V-068 / V-070 だけ（→ [05 §D-5](05_バリデーション規則.md)） |
| I-13 | **Skeletal Mesh では ARMATURE モディファイアを適用せず、複製の参照先を複製 Armature に繋ぎ直す** | 適用するとスキニングが壊れる。かつ元を指したままにすると「元シーンを汚さない」が成立しない（方針 D-4）。参照先の付け替えは結合テストで機械的に検証している（docs/99 P-0b の教訓） |
| I-14 | **FBX に書き出されるボーンを事前に予測してマニフェストに載せる** | `use_armature_deform_only` はウェイトの無いボーンを落とす。予測しないと「マニフェストにあるのに FBX に無いボーン」が生まれる。落ちたボーンを親に持つボーンは**残っている最も近い祖先に繋ぎ直す** |
| I-15 | **往復で保存されない量を検証項目にしない** | FBX は関節のトランスフォームしか持たないため**末端ボーンの長さは保存されない**（実測 0.25 m → 0.35 m）。`isLeaf` を持たせて比較対象から外した（docs/99 P-11） |
| I-16 | **フォルダ構成と出力先ルートをプリセットで宣言する**（`dccLayout` / `destination.environments`） | コードに埋め込むと現場の運用に合わせられない（方針 D-2）。出力環境の既定を `dev` にして、**明示しない限り本番に書かない**フェイルセーフにした |
| I-17 | **「どの比較項目の一致を要求するか」を `core/verify.py` に1つだけ置く** | 往復テストとボタン経路の結合テストの**両方**が必要とする。2か所に書くと必ずずれる。bpy にも unreal にも依存しない場所に置いたので単体テストもできる |
| I-18 | **「比較できなかった」は不合格として扱う** | 一致の証拠が無いまま緑にすると、**検証していない項目を検証済みと誤認する**。`morphTargets` / `sockets` は**両方とも空でも項目を出す**ようにした（「比較できなかった」と「どちらも 0 件で一致した」は意味が違う） |
| I-19 | **インポータが作ったものは値まで実測し、信用できなければ作り直す** | Interchange は `SOCKET_` 命名からソケットを自前で作るが、**scale に単位換算の 100 倍が混入する**（実測）。存在確認だけで合格にすると壊れたまま出荷する。コリジョンの I-8 と同じ構図（方針 D-6） |
| I-20 | **重複の検知には「総数の実測」が必要** | `find_socket()` は**先頭1個しか返さない**ため、同名が2個あっても気づけない。`get_sockets_by_tag("")` で全列挙して総数を比較する |
| I-21 | **命名規約のパーサに曖昧さが残るなら、文脈（実在する名前の集合）を渡す** | `UCX_Crate_01` は「本体 `Crate_01` の連番なし」とも「本体 `Crate` の 1 番」とも読める。`<名前>_<2桁>` は本プロジェクトの標準的なメッシュ名なので、文字列だけで解こうとすると誤読が常態化する（→ [99 P-19](99_作業ルール.md)） |

### 6.3 要決定: LOD のオブジェクト命名規約（**規約そのものに欠陥があった**）

#### 何が間違っていたか

[docs/04 §2.2](04_命名規約.md) はこう書いていました。

| コレクション名 | `LOD0` / `LOD1` / ... 連番・欠番なし。`LOD0` 必須 |
| **同名オブジェクト** | **LOD 間でオブジェクト名が同じでよい（コレクションで区別されるため）** |

**これは Blender では成立しません。**オブジェクト名は `.blend` 内で一意で、
コレクションは名前空間を作りません。実測（Blender 5.2.2 / 新規シーン）:

```
LOD0 に "Crate_01" を作る        → "Crate_01"
LOD1 に "Crate_01" を作る        → "Crate_01.001"   ← 別コレクションでも .001 が付く
obj.name = "Crate_01" で書き戻す → "Crate_01.001"   ← 戻らない
```

しかも [docs/99 P-0](99_作業ルール.md) に「`.001` は FBX のノード名を壊す」と
自分で書いてあります。**規約が既知の落とし穴と矛盾していました。**
LOD の収集ロジックが実機で一度も動いていなかったため、見つかっていませんでした。

#### 提案（**要承認**）

**オブジェクト名のサフィックスを規約として認める。**出力時のリネームはしない。

| 項目 | 新しい規約 |
|---|---|
| LOD レベルの決定 | **コレクション名（`LOD0` / `LOD1` / ...）が唯一の正**。オブジェクト名は見ない |
| オブジェクト名 | **一意であること**（Blender の制約）。`<本体名>_LOD<n>` を推奨 |
| LOD 間のベース名 | **揃えることを推奨**（`Crate_01_LOD0` / `Crate_01_LOD1` / ...）。違っていても動くが警告を出す |
| LOD 階層の必須性 | **必須ではない**。Nanite を使う場合 LOD は不要（既に `lod.mode = "none"` が既定） |

#### 「出力時にリネームする」案を採らない理由

| # | 理由 |
|---|---|
| 1 | **LOD は LOD ごとに別 FBX**（設計 I-4）。UE 側は LOD スロットに**明示的なインデックス**で割り当てるので、**FBX のノード名は LOD の組み立てに関与しない** |
| 2 | **アセット名はコレクション名から決まる**（`collect_from_collection`）。オブジェクト名に依存していない |
| 3 | リネームは `prepare.py` の最も危険な部分。**P-0 / P-0b で2回事故を踏んでいる**（`.001` 混入 / 退避名の復元漏れ）。**利益が無いのにリスクを増やす** |
| 4 | 人間が Blender を見たとき `Crate_01_LOD2` と書いてあるほうが分かりやすい。規約を実態に合わせるほうが素直 |

> **コレクションで分ける利点はそのまま残ります**（ビューレイヤでのプレビュー、
> 複数オブジェクトに分かれる場合の表示切り替え）。ユーザーの指摘どおりです。
> 変えるのは「オブジェクト名を同じにしてよい」という**実現不可能な一文だけ**です。

#### 併せて足したい検証ルール（提案）

| ID | 重大度 | 内容 |
|---|---|---|
| V-051 | ⚠ | **オブジェクト名の `_LOD<n>` サフィックスが、入っているコレクションのレベルと一致する**。`LOD2` の中に `Crate_01_LOD1` があったら警告（人間が読み違える） |
| V-052 | ⚠ | **LOD 間でベース名が揃っている**。`Crate_01_LOD0` と `Crate_02_LOD1` のような食い違いは複製事故の兆候 |

> どちらも**警告**です。サフィックスを付けない運用も許す（レベルはコレクションが決めるので）。

## 7. 既知の制約

- **commandlet モードでも Skeletal Mesh の取り込みは成功します**（2026-10-11 / A-12 で確認）。
  `SkeletonModifier` も commandlet で動くため、[docs/99](99_作業ルール.md) P-5 の制約は
  **`StaticMeshEditorSubsystem` 固有**で、リフレクション経由の他の API には及びません
- **LOD は UE 側が未実装です。**Blender 側は LOD ごとに別 FBX を書き出して
  `staticMesh.lod.levels` に記録していますが、**`importer.py` はそれを読んでいません**（→ T-5）
- **コレクションモード（`collect_from_collection`）は統合テストで一度も通っていません。**
  登録済み7サンプルはすべて選択モードです。**LOD コレクションを honor するのは
  コレクションモードだけ**なので、LOD の収集ロジックは実機で動いた実績がありません
- **末端ボーン（`isLeaf`）の長さは FBX 往復で保存されません。**検証項目にしないでください（docs/99 P-11）
- **`vertexCount` は FBX の往復で必ず増えます**（S-01: 13 → 40 / S-04: 96 → 216 / S-05: 563 → 3053 / S-06: 170 → 844）。
  UV シームと分割法線で頂点が割られるためで、**一致を要求しません**（記録はします / `core/verify.py`）
- **LOD は未検証です。**S-07 がサンプル側の要修正で止まっています（→ T-5 / A-10）
- **再インポート時の設定保持（`reimportPolicy`）は未実装です。**UE 側で変更した
  Nanite / LOD / コリジョン / マテリアル割当は、再インポートで失われうる（→ T-7）
- **調査で作った一時アセット `/Game/_Dev/Samples/S98_SocketProbe` が残っています。**
  保存されていない新規パッケージは Python から削除できませんでした
  （`delete_asset()` / `delete_directory()` がどちらも `False`。`collect_garbage()` 後も同じ）。
  **保存せずに UE を閉じれば消えます。**気になる場合は Content Browser から削除してください
- Blender の `jewelcraft` アドオンが headless 実行時に GPU 初期化エラーを出しますが、**本ツールの動作には影響しません**（Blender 側のログに出るだけ）
- `jq` がこの環境に無いため、マニフェストの JSON Schema 検証は `tools/validate_manifest.py`（システム Python + `jsonschema`）で行います。Blender / UE の Python では**構造チェックのみ**です
