## 1. 全体構成

### 1.1 コンポーネントと層

Q-17 の決定（「Blender→アセット元データ」と「アセット元データ→UE」を独立させる）により、
**2層 + トリガー**構造を正とする（[90 §2-1](90_オープン課題.md)）。

```
┌── 第1層: Blender → アセット元データ ───────────────────────────────┐
│ [A1] シーン走査     収集（コレクション / 選択）→ AssetSpec           │
│ [A2] バリデータ     事故条件の検出（docs/05）                        │
│ [A3] ジオメトリ整形 複製・トランスフォーム焼込・三角形化（D-4）        │
│ [A4] エクスポータ   FBX 出力（LOD ごとに別ファイル）                  │
│ [A5] マニフェスト   onepochi.json 出力                               │
│ [A6] UI パネル      ワンポチボタン / プリセット選択 / 結果表示         │
└──────────────────────────┬─────────────────────────────────────────┘
                           │ 成果物はアセット元データフォルダに残る（§4.1）
                           │   <AssetName>/fbx/{*.fbx, onepochi.json}
                           ↓ 渡すのは onepochi.json のパスだけ
┌── 第2層: アセット元データ → Unreal Engine 5.8 ─────────────────────┐
│ [C1] マニフェストローダ  JSON 読み込み + 構造検証 + 座標系の矛盾検出   │
│ [C2] インポートプランナ  マニフェスト → インポート設定へ解決          │
│ [C3] インポート実行      AssetImportTask（options=None → Interchange）│
│ [C4] ポストプロセス      コリジョン / ソケット / LOD / Nanite / MI    │
│ [C5] レポータ            ue_report.json（実測値との突合を含む）       │
│                                                                     │
│ ★ 中核は import_from_manifest(manifest_path) -> report              │
│   この関数は「起動方法を一切知らない」純粋な処理（方針 D-1）          │
└──────────────────────────┬─────────────────────────────────────────┘
                           ↑ 第2層を叩くトリガーは3つ。どれも同じ関数を呼ぶ
            (a) UE エディタのボタン（Editor Utility Widget）
            (b) HTTP ＝ Blender の UI ボタンから直接（★ これが「ワンポチ」）
            (c) コマンドライン（将来の CI / バッチ）
```

この構造の利点: 第2層は **FBX と `onepochi.json` しか見ない**ため、
将来 Houdini から同じものを出力すれば **UE 側は無改造で動く**（方針 D-5 / Q-17）。

### 1.2 設計方針（重要・v0.1 から変更なし）

| # | 方針 | 理由 |
|---|---|---|
| D-1 | **UE側のコア処理を「マニフェストのパスを渡すと取り込む」純粋な関数**として実装する | 起動方法（手動ボタン / HTTP / CI バッチ）を後から差し替えられる。「ワンポチ」の実現方式を仕様で固定しない |
| D-2 | **DCC側は「設定を決めない」。設定はプリセット + マニフェストで宣言する** | 規約をコードから分離し、プロジェクトごとに差し替え可能にする |
| D-3 | **バリデーションは DCC 側（上流）で行う** | UEに持ち込んでから気づくのを防ぐ。修正はDCC側でしかできない |
| D-4 | **破壊的なジオメトリ整形は必ず複製オブジェクト上で行い、元シーンを汚さない** | アーティストの作業データを守る。Undo依存にしない |
| D-5 | **DCC非依存の中間層（マニフェスト）を定義する** | Houdini 対応時に UE 側を作り直さない（Maya は Q-17 で対象外） |
| D-6 | **UE側の「お作法」はポストプロセスに寄せる** | インポータの対応範囲に引きずられない。Interchange の仕様変更に強い |

> **D-1 の具体化（v0.2 で追記）**: D-1 は §1.1 / §2 の「**2層 + トリガー**」として具体化された。
> `import_from_manifest(manifest_path, allow_failed, dry_run, report_path) -> report` が第2層の唯一の入口であり、
> (a) エディタボタン / (b) Remote Control API / (c) コマンドライン はすべてこの関数の**薄いトリガー**にすぎない。
> 実装は `tools/ue_plugin/onepochi_ue/importer.py`、トリガー (c) は `tools/ue_plugin/run_import.py`。

## 2. 起動方式（ワンポチの実現方法）

**B案（Remote Control API）を正式採用する。**A は「トリガーの1つ」として残し、C は非採用。

| 経路 | 仕組み | 位置づけ |
|---|---|---|
| **(b) Remote Control API 経由**（旧 B案） | Blender が書き出し後、UE の Remote Control（HTTP）へリクエストし `import_from_manifest()` を実行させる | **★ 正式採用。**これが「ワンポチ」の本体 |
| **(a) UE エディタのボタン**（旧 A案） | Editor Utility Widget / コンソールから `run_import.py` を叩く | **併存。**UE 未起動でも書き出せる経路として必要。デバッグの基本手段 |
| **(c) コマンドライン** | `UnrealEditor-Cmd` などから同じ関数を呼ぶ | 将来の CI / バッチ。仕様上の席のみ |
| ~~(d) UE 側フォルダ監視~~（旧 C案） | UE 常駐処理が中間フォルダを監視し自動取り込み | **非採用。**暗黙実行で事故る。(b) で足りる |

### 2.1 Remote Control API 経由の取り込み依頼（実測）

実装は `tools/dcc_blender/addons/onepochi/core/ue_bridge.py`（Blender 側・bpy 非依存・標準ライブラリのみ）と
`tools/ue_plugin/onepochi_rc.py`（UE 側の受け口）。

#### 2.1.1 やりとりの流れ

```
Blender                                        UE エディタ（起動中）
───────                                        ────────────────────
① onepochi.json を書く（第1層の成果物）
② 前回の ue_report.json を削除
   （残っていると古い結果を成功と誤認する）
③ HTTP PUT http://127.0.0.1:30010/remote/object/call
     objectPath   = /Script/PythonScriptPlugin.Default__PythonScriptLibrary
     functionName = ExecutePythonCommandEx
     parameters.pythonCommand  = 1行の Python 文（セミコロン区切り）
     parameters.executionMode  = ExecuteStatement
   ───────────────────────────────────────────>  PythonScriptLibrary.ExecutePythonCommandEx
                                                  └ onepochi_rc.handle(manifest, report,
                                                                       dry_run, allow_failed)
                                                     └ onepochi_ue.importer.import_from_manifest()
⑤ ue_report.json を読んで UI に出す  <───────────  ④ ue_report.json を書く
```

| 項目 | 値 | 根拠 |
|---|---|---|
| HTTP メソッド | **PUT**（POST ではない） | 実測（`/remote/object/call`） |
| 既定ポート | HTTP **30010** / WebSocket **30020**。**どちらも開いており `/remote/info` が応答する**（実測） | `tools/presets/project_default.json` / 実機 |
| 送る Python 文 | **1行（セミコロン区切り）に収める。**`if` などの複合文は実行モードで解釈が変わるため分岐を入れない | `ue_bridge.build_import_statement()` |
| 併用プラグイン | `Python Editor Script Plugin`（無いと `Could not find object` になる） | 実測のエラー分類 |
| タイムアウト | プリセット `ue.timeoutSeconds`（既定 **180 秒**） | `tools/presets/project_default.json` |

> **設計上の約束（重要）**: **結果は `ue_report.json` から取る。HTTP レスポンスの形からは判定しない。**
> レスポンス構造は UE のバージョンで変わりうるため（[99 P-6 / P-7](99_作業ルール.md) の教訓）。
> HTTP は「依頼が届いたか」だけを判定し、**レポートが生成されていなければ失敗扱い**にする
> （「依頼は届いたが中で落ちた」を成功と誤認しないため）。

#### 2.1.2 UE 側に必要な2つのセキュリティ設定（実測。既定はどちらも OFF）

**Remote Control API プラグインを有効にしただけでは通らない。**実機では次のエラーで拒否された:

```
HTTP 400
Object Default__PythonScriptLibrary cannot be accessed remotely,
check remote control project settings.
```

エンジンのソース（`RemoteControlSettings.h` / `RemoteControlModule.cpp` の
`CanBeAccessedRemotely` / `WebRemoteControlInternalUtils.cpp`）を読むと、
**2つの設定が独立にゲートしている**。場所は
**`Project Settings > Plugins > Remote Control > 「Remote Control | Security」`**。

| # | 設定 | 内容 | 注意 |
|---|---|---|---|
| 1 | **Restrict Server Access** (`bRestrictServerAccess`) | サーバアクセスの制限 | **★ これを先に ON にしないと 2 のチェックボックスが押せない**（2 の UI 編集条件になっている） |
| 2 | **Enable Remote Python Execution** (`bEnableRemotePythonExecution`) | リモートからの Python 実行を許可 | 1 を ON にしてから |
| 3a | **Custom Allowed Remote Function Calls** (`CustomAllowedRemoteFunctionCalls`) | 関数の許可リストに `PythonScriptLibrary` / `ExecutePythonCommandEx` を追加 | **推奨。**許可範囲が狭い |
| 3b | Allow Any Remote Function Call (`bAllowAnyRemoteFunctionCall`) | 任意の関数呼び出しを許可 | 簡単だが**許可範囲が広い** |

- 3 は **3a か 3b のどちらか**でよい。許可リストに入っていないと
  `... is not allowed by remote control settings` で拒否される
- 設定の保存先は **プロジェクトの `Config/DefaultRemoteControl.ini`**、
  セクション `[/Script/RemoteControlCommon.RemoteControlSettings]`
  （`URemoteControlSettings` が `UCLASS(config = RemoteControl)` のため）

#### 2.1.3 失敗の切り分け（日本語メッセージ + 具体的な手順）

`ue_bridge.classify_failure()` が UE のエラー文から原因を特定し、**日本語で対処手順まで**返す（Q-18）。

| 検出するもの | 原因 | 返すもの |
|---|---|---|
| `cannot be accessed remotely` | §2.1.2 の 1 / 2 が OFF | 「Restrict Server Access を先に ON にしてから Enable Remote Python Execution」 |
| `is not allowed by remote control settings` | §2.1.2 の 3 が未設定 | 許可リストへの追加（推奨）または Allow Any Remote Function Call |
| `Could not find object` | Python プラグインが無効 | 「Python Editor Script Plugin を有効に」 |
| HTTP 404 | Remote Control API プラグインが無効 | プラグインの有効化 |
| 接続拒否 | UE 未起動 / ポート違い | 起動・プラグイン・ポート番号の3点確認 |
| タイムアウト | シェーダコンパイル等で長時間化 | UE の Output Log を確認 |

> **現状（2026-10-10）**: **実装済み。HTTP の経路と失敗経路は実機の UE 5.8.3 に対して検証済み。**
> ただし **§2.1.2 の2つの設定がまだ OFF のため、成功経路（実際にアセットが生成されるところ）は未検証**。
> 設定の投入は [12 §6.2 A-2](12_実装状況.md) でユーザー作業として依頼中（→ §14.2）。

### 2.2 公式 MCP プラグインを実行経路にしない理由

UE 5.8 に同梱されている Epic 公式の MCP プラグインは**有効化済み**だが（Q-01b）、
**開発・検証の補助に限定**し、ワンポチツール本体の実行時依存にはしない。

| 理由 | 実測内容 | 出典 |
|---|---|---|
| Experimental かつ AI エージェント向け | 製品の実行経路として安定性を前提にできない | CLAUDE.md / 90 Q-01b |
| Interchange を迂回する | `StaticMeshTools.import_file` は `FbxFactory` + `FbxImportUI` を**ハードコード**している | [11 §5](11_UE環境実測.md) |
| 再インポートできない | 同ツールは `replace_existing=False` **固定** | [11 §5](11_UE環境実測.md) |

→ **本番経路は UE Python + `AssetImportTask`（`options=None` で Interchange 既定パイプライン）**。
細かい設定はポストプロセスに寄せる（方針 D-6 / [12 I-6](12_実装状況.md)）。

## 3. データフロー

```
① Blender で対象を指定（選択オブジェクト or アセット用コレクション）
② [ワンポチ] ボタン
③ 設定の合成（§10.2: プリセット → onepochi_asset.json → UI 指定）
④ バリデーション実行（docs/05）
    ├─ Error が1件以上 → 中断。パネルに一覧表示（行クリックで該当オブジェクトを選択）
    └─ Warning のみ   → 続行（上限値超過はすべて warning / Q-06）
⑤ 対象を複製し、トランスフォーム焼込・三角形化など整形（D-4）
⑥ FBX 出力（LOD ごとに別ファイル）+ onepochi.json 出力
       → <AssetName>/fbx/ （§4.1）
⑦ (b) Blender から UE へ HTTP 依頼 ／ (a) ユーザーが UE でボタンを押す
⑧ UE: マニフェスト読み込み → 構造検証 → 座標系の矛盾検出 → インポート設定に解決
⑨ UE: インポート実行（AssetImportTask / Interchange）
⑩ UE: ポストプロセス（Nanite / ライトマップ / コリジョン / ソケット / ビルド設定 / MI）
⑪ UE: 実測 → マニフェストの stats と突合（comparison）→ 保存 → ue_report.json
⑫ 結果を DCC 側パネル（(b) 経路）または UE のログ・通知（(a) 経路）で表示
```

### 3.1 失敗時の扱い

| フェーズ | 失敗時 |
|---|---|
| ④ バリデーション | 書き出しを行わない。`fbx/` に何も作らない |
| ⑥ 出力 | 当該アセットの書き出しを中断し、指摘を UI に出す（元シーンは複製で作業しているため無傷 / D-4） |
| ⑧ マニフェスト検証 | インポートを開始しない。`validation.status = failed` のマニフェストは**拒否**（`allowFailed` で明示的に上書き可） |
| ⑧ パス検証 | `destination.pathWhitelist` の配下でない書き込み先は**拒否**（[03 §6.1](03_マニフェスト仕様.md)） |
| ⑨ インポート | 当該アセットを `failed` としてレポートに記録し、**他のアセットの取り込みは続行**する（`result` は `partial`） |
| ⑩ ポストプロセス | アセットは残す。失敗した API 呼び出しを個別に warning としてレポートに残す（[12 I-5](12_実装状況.md)） |

> **要検証**: インポート失敗時のロールバック手段（新規作成アセットの削除 / 再インポート時の原状復帰）。
> 現在の実装は**ロールバックせず、レポートに残す**方式（[12 I-5](12_実装状況.md)）。

### 4.1 アセット元データフォルダ構成（`ExchangeRoot` 方式は廃止）

**中継置き場（`ExchangeRoot`）は廃止した**（Q-07 / [90 §2-3](90_オープン課題.md)）。
FBX は `.blend` の隣に置くのが最も追跡しやすく、コピーの二重管理も起きない。
また (b) の Blender → UE 直接依頼であれば「UE が探しに行く」必要がそもそも無い。

```
<AssetsRoot>/
└── Crate_01/                      ← フォルダ名 = アセット名（先頭数字禁止 / 04 §0 N-1）
    ├── Crate_01.blend             ← 元データ
    ├── onepochi_asset.json        ← ★ 人間が書く設定（UE インポート先 / プリセット名 等）
    ├── fbx/
    │   ├── SM_Crate_01.fbx        ← 書き出し成果物（LOD0）
    │   ├── SM_Crate_01_LOD1.fbx   ← LOD ごとに別ファイル（§5.4）
    │   ├── onepochi.json          ← ★ ツールが書くマニフェスト。UE 側はこれだけを見る
    │   └── ue_report.json         ← UE 側レポート（既定の出力先）
    ├── textures/                  ← UE に持っていくテクスチャ
    ├── substance/                 ← 作業データ（UE には持っていかない）
    └── houdini/                   ← 作業データ（UE には持っていかない）
```

| ファイル | 書く主体 | 役割 |
|---|---|---|
| `onepochi_asset.json` | **人間**（テキストエディタで直接編集可） | UE インポート先パス・プリセット名・アセット種別など。実装済み（`core/presets.py`） |
| `onepochi.json` | **ツール** | `onepochi_asset.json` + プリセット + シーン実測値を展開した**最終値**。仕様は [03](03_マニフェスト仕様.md) |

- `assets[].sourceFile` / `lod.levels[].sourceFile` は**マニフェストファイル自身からの相対パス**（= `fbx/`）。
  フォルダを移動しても壊れない（[03 §5.1](03_マニフェスト仕様.md)）
- 実行ログは `%LOCALAPPDATA%/OnePochi/runs/<run_id>/` に置く。**メッシュは置かない**（小さな JSON だけなので
  容量を気にせず 30日保持）。`run_id` はマニフェストの `runId` と一致させる（[90 §2-3](90_オープン課題.md)）
- **上図のフォルダ名はすべてプリセットの `dccLayout` で変更できる**（R-1 の解決 → §10.3）。
  コードにハードコードしていないので、既存のフォルダ運用に合わせられる。
  `AssetsRoot` は「`.blend` の置き場」が既定であり、ツールは**特定の親フォルダを前提にしない**

> **実装メモ**: 現状、UE 側のジョブファイルは `%LOCALAPPDATA%/OnePochi/job.json` に置く実装（`run_import.py`）で、
> レポートの既定出力先はマニフェストと同じ `fbx/ue_report.json`。
> **`runs/<run_id>/` への実行ログ集約は未実装**（→ §13 P3）。

## 5. Static Mesh 仕様

### 5.1 マニフェストで制御する項目

既定値は `tools/presets/project_default.json` の実値。マニフェストの明示値が常に優先（D-2）。

| 項目 | 既定値 | 備考 |
|---|---|---|
| 出力先パス | `/Game/_Dev/{assetName}`（プリセットの `pathTemplate`） | 検証中は `/Game/_Dev` 固定（→ [90 §3 R-2](90_オープン課題.md)） |
| 書き込み先ホワイトリスト | `["/Game/_Dev"]` | **配下以外への書き込みを UE 側が拒否**（事故防止 / [03 §6.1](03_マニフェスト仕様.md)） |
| アセット名 | `SM_<Name>` | 命名規約は [04 §1](04_命名規約.md) |
| Nanite 有効 | `false` | **既定 OFF。プリセット `environment` では ON**（Q-05） |
| Nanite Fallback 相対誤差 | `1.0` | Nanite 有効時のみ |
| LOD 生成方式 | `none` / `auto` / `manual` | **`manual` はコレクション方式**（§5.4） |
| LOD 自動生成数（`auto`） | `environment` は `3` | `autoLodCount`（1〜8） |
| Simple Collision | `fromDCC` | `fromDCC` = `UCX_` 等を使用 / `auto` / `none` |
| Complex Collision | `default` | `simpleAsComplex` / `complexAsSimple` |
| ライトマップUVチャンネル | `1` | UV0=テクスチャ、UV1=ライトマップ |
| ライトマップ解像度 | `64`（`environment` は `128`） | |
| 法線の再計算 | `false` | DCC 側の法線を尊重 |
| 接線の再計算 | `true` | |
| 退化三角形の除去 | `true` | |
| Distance Field 生成 | `true` | |
| Build Scale | `(1,1,1)` | 原則1。スケール調整は DCC 側で解決させる |
| Vertex Color 保持 | `true`（`mode = replace`） | Skeletal Mesh とは既定が逆 |
| マテリアルスロット | DCC 側のスロット名を保持 | **`index` で順序を固定**（[04 §2.6](04_命名規約.md)） |
| ソケット | マニフェストで明示 | §8 |
| 再インポート時の設定保持 | `preserveSettings` | §5.5 |
| しきい値 | `maxMaterialSlots: 8` / `maxCollisionTrianglesPerShape: 32` / `maxTextureResolution: 4096` | **超過は警告。書き出しは止めない**（Q-06 / [90 §2-4](90_オープン課題.md)） |

### 5.2 コリジョン

DCC 側で以下のプレフィックスを持つメッシュをコリジョンとして扱う（UE の FBX インポータ規約準拠 / [04 §2.3](04_命名規約.md)）。

| プレフィックス | 形状 |
|---|---|
| `UCX_<MeshName>_##` | 凸包（Convex） |
| `UBX_<MeshName>_##` | ボックス |
| `USP_<MeshName>_##` | スフィア |
| `UCP_<MeshName>_##` | カプセル |

| 検証 | 重大度 | ルール |
|---|---|---|
| プレフィックスが規約どおり | ✖ エラー | V-040 |
| 対応する本体メッシュが存在する | ✖ エラー | V-041 |
| `UCX_` が閉じた多面体である | ✖ エラー | V-042 |
| `UCX_` が凸である | ⚠ 警告 | V-043 |
| 三角形数が上限以内 | ⚠ **警告**（Q-06） | V-044 |

- サンプル `02_static_collision` で **`UCX_` が凸でない（8/13面）** ことを実際に検出済み（[12 §4.1](12_実装状況.md)）
- インポート後、UE 側で主アセット以外のアセットが生成された場合は
  「コリジョンが別アセットになっていないか」を警告としてレポートに残す実装になっている

#### プレフィックス規約は Interchange 経由でも機能する（実測で確定）

**UE 5.8 の Interchange 経由でもこのプレフィックス規約は従来どおり機能する**（[12 §4.4](12_実装状況.md) / 2026-10-10 実測）。

| 事項 | 実測結果 |
|---|---|
| `02_static_collision` のコリジョン | **`convex: 1` + `box: 1`** が期待どおり StaticMesh の簡易コリジョンとして入った |
| 別アセット化 | **しない。**`UCX_` / `UBX_` メッシュが独立した StaticMesh にはならなかった |
| コリジョン数の読み出し | `body_setup.agg_geom` の `convex_elems` / `box_elems` / `sphere_elems` / `sphyl_elems` の長さ |

> **ただし自動生成に注意**: **コリジョンメッシュを含まない FBX をインポートすると、Interchange が凸コリジョンを1個自動生成する。**
> マニフェストが `collision.simple = "none"` を宣言している場合は、**ポストプロセスで `agg_geom` の各配列を空にして
> 宣言どおりの状態にする**（方針 D-6 / [12 I-8](12_実装状況.md)）。
> `01_static_minimal` / `03_static_multislot` で collisionShapes 0 個が得られているのはこの処理の結果。

### 5.3 マテリアルスロット

- Blender のマテリアル名は **`M_<名前>` 形式が必須**。違反は**書き出しを中断**（V-003c / Q-19 → §7）
- スロット順は Blender 上の並びに依存させず、マニフェストの `index`（0 始まり・欠番なし）で固定する
- サンプル `03_static_multislot` で `M_Slot_A, M_Slot_B, M_Slot_C` が **index 順に固定されることを確認済み**
  （[12 §4.1](12_実装状況.md)）

### 5.4 LOD —— コレクション方式（v0.2 で変更）

**オブジェクト名の `_LOD0` サフィックス方式は廃止。**Blender のコレクション名で LOD を表す
（Q-11 / [90 §2-2](90_オープン課題.md) / [04 §2.2](04_命名規約.md)）。

```
Crate_01/                 ← アセット用コレクション（名前 = アセット名）
├── LOD0/                 ← 必須。欠番不可。オブジェクト名に _LOD は付けない
│   └── Crate_01
├── LOD1/
│   └── Crate_01
├── Collision/
│   ├── UCX_Crate_01_01
│   └── UBX_Crate_01_01
└── Sockets/
    └── SOCKET_Lid
```

| 規則 | 内容 | ルール |
|---|---|---|
| コレクション名 | `LOD0` / `LOD1` / … 連番・欠番なし | V-045 / V-045a |
| LOD 階層なし | LOD コレクションが無い場合は「LOD0 のみ」とみなす（単純なアセットに階層を強制しない） | — |
| 予約名 | `LOD<n>` / `Collision` / `Sockets` は予約語 | V-045b |
| 同名オブジェクト | LOD 間でオブジェクト名が同じでよい（コレクションで区別される） | — |
| スロット構成 | 全 LOD でマテリアルスロット構成が一致していること | V-046 |
| 三角形数 | LOD レベルの上昇に対して単調減少していること | V-047（⚠） |

**LOD ごとに別 FBX を書き出す**（[12 I-4](12_実装状況.md)）。
FBX の LOD グループ規約（`LOD_<name>` ノード）に依存すると UE 側の解釈に引きずられるため、別ファイルにして確実にする。

| 項目 | 実装 |
|---|---|
| ファイル名 | `<UEアセット名>_LOD<n>.fbx`（例 `SM_Crate_01_LOD1.fbx`）。LOD0 は `<UEアセット名>.fbx` |
| マニフェスト | `staticMesh.lod.levels[].sourceFile` が**必須**（[03 §11.4](03_マニフェスト仕様.md)） |

プリセットごとの既定（[90 §2-2](90_オープン課題.md)）:

| プリセット | Nanite | LOD | 理由 |
|---|---|---|---|
| `environment`（PC/PS5 背景） | ON | `auto`（`autoLodCount: 3`） | Nanite の Fallback Mesh 用 |
| `environment_mobile`（Switch/モバイル背景） | OFF | `manual` | Nanite が使えない経路 |
| `prop` | OFF | `none`（必要なら `manual`） | 小物に階層を強制しない |
| `character` | OFF | `none` | スケルタル LOD は v2 |

> **Nanite があれば LOD 不要か** → **対象に Switch とモバイルが入るため「不要」とは言えない**（Q-04）。
> また **Skeletal Mesh には Nanite が効かない**（UE 5.8 での対応状況は **要検証** / [90 §2-2](90_オープン課題.md)）。
> なお UE の Static Mesh の LOD は**アセット内部**に格納されるため、LOD が UE のアセット一覧を増やすことはない。

### 5.5 再インポート時の設定保持

既存アセットが存在する場合、以下は **UE 側の現在値を維持**する
（`reimportPolicy.mode = preserveSettings`。`override[]` に挙げた項目のみ強制上書き）。

- Nanite 設定 / LOD 設定 / コリジョン設定 / ライトマップ設定 / マテリアル割当 / ソケット / ビルド設定

ジオメトリ（頂点・UV・法線・スキン）は常に **DCC 側を正**とする。

> **未実装**: 保持処理そのもの（マニフェストに値は入るが UE 側は未対応 / [12 T-7](12_実装状況.md) → §13 P3）。

#### `use_armature_deform_only` との相互作用（重要）

プリセット `character` は FBX 書き出し時に **`use_armature_deform_only: true`** を指定する。
これは **ウェイトを持たない（`use_deform` でない）ボーンを FBX から落とす**設定で、
ボーン数を抑えられる反面、**ルートボーンにウェイトが無いとルートごと消える**。

- 対策として、ツールは**実際に書き出されるボーン名の集合を事前に予測する**
  （`skeletal.exported_bone_names()`: deform なボーンとその**祖先すべて**を残す）。
  予測した集合だけをマニフェストの `skeleton.bones[]` に載せる
- 落とされたボーンを親に持つボーンは、**残っている最も近い祖先に繋ぎ直す**
  （宙ぶらりんの親参照を作らない）
- それでも**ルート自身にウェイトが無い場合は V-062 のエラー**にする。
  対処は「ルートに少量のウェイトを割り当てる」か「プリセットで
  `use_armature_deform_only` を `false` にする」のどちらか

> 予測と FBX の実際の内容が一致することは、**書き出した FBX を Blender に読み戻す結合テスト**で担保する
> （`tools/dcc_blender/tests/test_integration_skeletal.py`）。S-04 では
> `root` / `bone_01` / `bone_02` の3本が親子関係ごと保存されることを確認済み。

> **要検証**: UE 5.8 のプラットフォーム別ボーン数上限（[90 §2-4](90_オープン課題.md) / [05](05_バリデーション規則.md)）。

### 6.3 Skeleton 流用（UC-05）—— 互換判定を2モード化（v0.2 で変更）

マニフェストに `skeleton.mode = "reuse"` と `skeleton.assetPath` を指定する。
**ボーン階層の互換性チェックをインポート前に行い**、不一致なら中断する（インポートしてから壊れるのを防ぐ）。

判定モードを **2つから選べる**ようにした（Q-09 / [03 §12.4](03_マニフェスト仕様.md)）。

| `compatibilityMode` | 判定 | 想定する使い方 |
|---|---|---|
| **`exact`**（既定） | ボーン階層の**完全一致**を要求。`boneHierarchyHash` の一致で判定 | **量産時。**意図しない Skeleton のズレを確実に弾く |
| **`subset`** | `boneHierarchy` のペア集合が既存 Skeleton の**部分集合**なら許可 | **試行錯誤時。**ボーンを削った試作メッシュを既存 Skeleton に載せたいとき |

判定根拠はハッシュだけでなく**元データとしても持たせる**:

| フィールド | 内容 |
|---|---|
| `skeleton.boneHierarchy` | `[親ボーン名 or null, ボーン名]` を階層順に並べた配列 |
| `skeleton.boneHierarchyHash` | 上記を `"<親>><子>"`（親が無い場合は空文字）形式で **`"\n"` 連結 → UTF-8 → SHA-1**。`sha1:<hex>` 形式。**トランスフォームは含めない** |

#### 判定ロジックは実装済み（UE 非依存）

`tools/ue_plugin/onepochi_ue/skeleton_compat.py` の `compare(incoming, existing, mode)`。
**`unreal` を import していない**ため、UE を起動せずに単体テストできる（マニフェスト検証 21 件 + Skeleton 互換 35 件 + 受け口 10 件）。

| モード | 許す差分 | 許さない差分 |
|---|---|---|
| `exact` | なし | ボーン名・親子関係・**並び順**のいずれかの不一致、既存側の余分なボーン |
| `subset` | **既存 Skeleton 側に余分なボーンがあること**、並び順の違い | 取り込む側にあって既存に無いボーン、**親が違うボーン**、ルートボーンの不一致 |

> **`subset` でも親子関係の一致は必須。**名前が揃っていても親が違えば UE 側でバインドが破綻するため。

- 戻り値は `compatible`（bool）と **日本語の `reasons`**（Q-18）。そのまま UI / レポートに出せる
- ハッシュ算出は **Blender 側（`core/manifest.py`）と UE 側で同一実装**でなければならない。
  食い違うと「同じ階層なのに不一致」と誤判定する。
  `tools/dcc_blender/tests/test_core.py::TestCrossPackageHash` が**両者の一致を機械的に検証**している

> **要検証**: Interchange 経由での既存 Skeleton 指定方法と API（[11 §11 V-6](11_UE環境実測.md)。
> 公式 `import_file` のレガシー経路には `skeleton` 引数があるが、Interchange 側の対応プロパティは未確認）。
> **また、`compare()` を実際の Skeleton アセットから読み取った階層に対して動かす経路も未実装・未検証**（→ §6.8）。

### 6.5 スキンウェイトの方針（v0.3 で決定）

**「実害のあるものだけエラー、直せるものは複製側で直す」**を原則とする（方針 D-4）。

| 規則 | 内容 | 重大度 | 理由 |
|---|---|---|---|
| **V-068** | スキンウェイトが無い頂点 | ✖ **エラー** | UE で**原点に吸い寄せられる**実害がある。書き出させない |
| **V-070** | ウェイトの合計が実質ゼロ | ✖ **エラー** | V-068 と同じ実害 |
| **V-069** | 合計が 1.0 でない（正規化のズレ） | ⚠ **警告 + 自動修正** | 下記 |

#### V-069 を「エラーにしない」判断の根拠（実測）

当初は「ズレ < 0.01 なら警告、それ以上はエラー」を検討していたが、**実運用に耐えないため変更した**
（[14 §8.3](14_サンプル指摘.md)）。

| サンプル | ズレている頂点 | 最大ズレ |
|---|---|---|
| S-04 `04_skeletal_minimal` | **96 / 96**（全頂点） | `0.0230` |
| S-05 `05_skeletal_shared_skeleton` | **496 / 563** | `0.0247` |

- しきい値 `0.01` をエラーにすると、**ユーザーが修正済みのサンプル2件がどちらも書き出せなくなる**
- 手付けウェイトでは **1〜2% のズレが普通に出る**。UE も取り込み時に正規化する
- したがって **警告にして、書き出し時に複製側で正規化する**。
  自動修正したことは `auto_fixed` フラグ付きでマニフェストに必ず記録する（黙って直さない）
- **元シーンは変更しない**（方針 D-4）。正規化が効いていることは
  FBX を読み戻して確認済み（S-04: ズレ 96 頂点 → **0**）

#### 整形時の約束（Skeletal Mesh モード）

`prepare.py` は Skeletal Mesh のとき**スキニングを壊す整形を行わない**。

| 処理 | Static Mesh | Skeletal Mesh |
|---|---|---|
| ARMATURE モディファイアの適用 | （対象外） | **適用しない**（`PRESERVED_MODIFIER_TYPES`）。そのため V-011 の警告対象からも外す |
| モディファイアの参照先 | — | **複製メッシュの参照先を複製 Armature に繋ぎ直す**（元を指したままにしない） |
| 回転・スケールの焼き込み | 行う | **スキンされたメッシュには行わない** |
| ウェイトの正規化 | — | **複製側で行う**（V-069 の自動修正） |

### 6.7 FBX の制約: 末端ボーンの長さは往復で保存されない（実測）

| 項目 | 内容 |
|---|---|
| 症状 | Blender で長さ `0.25 m` にした末端ボーン `bone_02` が、FBX を読み戻すと **`0.35 m`** になる |
| 実測条件 | S-04 / Blender 5.2.2 / `add_leaf_bones=False` |
| 原因 | **FBX はボーンを「head→tail の線分」ではなく「関節（ノード）のトランスフォーム」として持つ。**子を持たないボーンは tail の位置を表現する手段が無く、インポータが推定する |
| 往復で保存されるもの | **ボーン名 / 親子関係 / head の位置** |
| 仕様への反映 | マニフェストのボーンに **`isLeaf`** を持たせる（v0.3.0）。**`isLeaf` なボーンの `lengthCm` を UE 側の検証項目にしてはいけない** |

> 出典: [99 P-11](99_作業ルール.md) / [14 §8.4](14_サンプル指摘.md)。
> 「Blender で見えている数値」と「FBX が持てる情報」は同じではない。
> **往復で保存されない量を検証項目に入れない。**

#### 既存 Skeleton の親子関係の読み出し（制約が解消）

当初は **ボーン名しか読めない**制約があった。`FReferenceSkeleton` がリフレクションに
載っていないため、`SkeletonModifier`（MeshModelingToolset）が必要で、しかも
`SkeletonModifier` は **SkeletalMesh を要求する**（取り込み前には対象のメッシュが無い）。

**解決**: `skeletal.find_mesh_for_skeleton()` が「その Skeleton を既に使っている
SkeletalMesh」を探して橋渡しする。手段は2つで、順に試す（UE 5.8.3 で両方とも実測）。

1. `Skeleton.get_skeleton_preview_mesh()` — Interchange が作った Skeleton には
   取り込み元のメッシュが入っている
2. アセットレジストリの `Skeleton` タグ検索 — プレビューメッシュが未設定でも、
   同じ Skeleton を参照するメッシュがあれば拾える（タグはロード不要で読めるので安い）

これで **取り込み前**に `compare()`（親子関係まで比較）が使える。
実測では S-05 の `exact` 判定が `method: "namesOnly"` → **`"skeletonModifier"`** に変わった。

| 状況 | 判定方法 | レポートの `method` |
|---|---|---|
| メッシュが見つかる（通常） | 親子関係まで比較 | `skeletonModifier` |
| 見つからない / `/Engine` 配下 | ボーン名の並びだけ | `namesOnly`（**検証できていないことを `reasons` に明記**） |

> `/Engine` 配下の Skeleton では `SkeletonModifier` が階層を読めない（実測）。
> その場合は `namesOnly` に落ちるが、**黙って合格にはしない**。

## 9. 座標系・単位の変換規則

| 項目 | Blender | Unreal Engine | 変換 |
|---|---|---|---|
| 単位 | 1.0 = 1 m | 1.0 = 1 cm (uu) | ×100 |
| Up 軸 | +Z | +Z | 一致 |
| Forward 軸 | -Y | +X | 要回転 |
| 手系 | 右手 | 左手 | Y 反転 |

**方針**: 変換は **FBX エクスポータの設定に寄せ、ツール側で行列を自前計算しない。**
ソケット等マニフェストに数値で持つものだけは明示的に変換し、
**変換規則をマニフェストの `coordinateSystem` に記録**して UE 側で検証できるようにする。

> ### ✅ 変換規則は実測で確定した（2026-10-10 / 要検証を解除）
>
> E2E 往復テスト（[12 §4.4](12_実装状況.md)）で、Blender の 1m 立方体（`-Y` 側に四角錐の突起）が
> UE 側で以下のとおりになることを実測しました。**DCC 側の予測と差分 0**。
>
> | 項目 | UE 実測値 |
> |---|---|
> | `boundsMin` | `(-50, -50, -50)` uu |
> | `boundsMax` | `(50, 83.7828, 50)` uu |
> | `dimensions` | `(100, 133.7828, 100)` uu |
>
> → **確定した変換**
>
> - **Blender `(x, y, z)` m → UE `(x, -y, z)` cm**（`-Y` の突起が UE では `+Y` 側に出た）
> - **`appliedScale` = 100 / UE 側 Import Uniform Scale = 1.0** で正しい（二重スケールなし）
>
> サンプル3件（`01` / `02` / `03`）すべてで dimensions `(100, 133.7828, 100)` / triangleCount `22` /
> uvChannelCount `1` が一致しています。**これは Static Mesh についての実測**です。

実測から分かった判定上の注意（[10 §7.1](10_サンプル実測.md)）:

- `dimensions` は `rotation_euler` を反映しない → **回転未適用の検出に `dimensions` は使えない**（`matrix_world` を見る）
- **負スケールは `dimensions` やワールド境界では検出できない** → `matrix_world.determinant() < 0` で判定する
- トランスフォームの焼き込みは **`bpy.ops.object.transform_apply` を使わず行列計算で行う**（headless で安定 / [12 I-2](12_実装状況.md)）

### 9.3 スケールの受け渡し（DCC → UE）

| 項目 | 値 | 意味 |
|---|---|---|
| `coordinateSystem.appliedScale` | `100.0` | **DCC 側で既に ×100 を掛けた**という宣言 |
| `coordinateSystem.conversionDoneBy` | `"fbx_exporter"` | 変換の実施主体（`tool` / `none` も可） |
| UE 側の Import Uniform Scale | `100.0 / appliedScale` = `1.0` | UE 側が逆算する。二重スケールを機械的に防ぐ |

UE 側は `appliedScale` が不正（欠落 / 0 以下）なら**インポートを開始しない**。
`targetUpAxis != "Z"` や `conversionDoneBy` が未知の値なら警告を出す。

さらに、マニフェストの `stats`（DCC 側の予測値）と UE 側の実測を突き合わせる
（`comparison` ブロック / [12 I-7](12_実装状況.md)）。
**座標系・単位の事故を機械的に検出する仕組み**であり、本章の規則が守られているかの実行時検証になる。

| 突合項目 | 比較内容 |
|---|---|
| `dimensions` | `stats.dimensionsCm` と UE 実測の `dimensionsUu`。軸別の差分と `matches`（許容 0.05） |
| `triangleCount` / `vertexCount` | DCC 側予測と UE 側 LOD0 実測の一致 |

**実測結果**: サンプル3件すべてで `comparison` の全項目が一致（`matches: true`）。
`appliedScale` 100 / Import Uniform Scale 1.0 の組み合わせが正しいことが機械的に確認されました。

> UE 側の実測は **`StaticMesh` 自身のメソッド**（`get_bounding_box()` / `get_num_triangles(0)` /
> `get_num_tex_coords(0)` 等）で行います。`StaticMeshEditorSubsystem` は
> **commandlet モードでは取得できない**ためです（[12 C-3](12_実装状況.md)）。

## 10. プリセット（設定ファイル）

規約をコードに埋め込まず、プリセットファイルで管理する（方針 D-2）。

### 10.1 実装された 7 種

```
tools/presets/
├── project_default.json       すべての親。FBX 設定（28 キー）の実体はここ
├── prop.json                  小物（Nanite OFF / LOD なし）

├── character_mobile.json      キャラクター（影響ボーン 4 / maxBones 128）
└── sample_debug.json          samples/ 検証用（先頭数字の命名を許容）
```

| プリセット | `extends` | 主な差分 | `pathTemplate` |
|---|---|---|---|
| `project_default` | — | 全既定値・FBX 設定・`limits`・`dccLayout`・`destination.environments`・`ue.*` | `{contentRoot}/{assetName}` |
| `prop` | `project_default` | Nanite OFF / LOD `none` / ライトマップ 64 | `{contentRoot}/Props/{assetName}` |
| `environment` | `project_default` | **Nanite ON** / LOD `auto`（3） / ライトマップ 128 | `{contentRoot}/Environment/{assetName}` |
| `environment_mobile` | `environment` | Nanite OFF / LOD **`manual`** / `maxMaterialSlots: 4` / `maxTextureResolution: 2048` | （`environment` を継承） |
| `character` | `project_default` | `skeleton.mode: create_new` / `physicsAsset.create: false` / FBX `object_types: [MESH, ARMATURE]` | `{contentRoot}/Characters/{assetName}` |
| `character_mobile` | `character` | `maxBoneInfluences: 4` / `maxBones: 128` / `maxMaterialSlots: 4` / `maxTextureResolution: 2048` | （`character` を継承） |

  実装は `tools/dcc_blender/addons/onepochi/core/presets.py`、単体テストで継承を検証済み
- プリセットは Git 管理し、チームで共有する。
  置き場を差し替えたいときは環境変数 **`ONEPOCHI_PRESET_DIR`**（スタジオ共有のプリセットを使う用）

### 10.2 設定の合成順序

**後のものが前を上書きする**（D-2: 明示値が常に優先）。

```
project_default  →  extends 連鎖  →  当該プリセット  →  onepochi_asset.json  →  UI の明示指定
（プロジェクト共通）                （種別ごと）        （アセットごと・人間が書く）  （その回だけ）
```

- `onepochi_asset.json` はアセットフォルダ直下に置く（§4.1）。無ければ空として扱う。
  ファイル名は環境変数 **`ONEPOCHI_ASSET_CONFIG_NAME`** で差し替えられる
- DCC 側 UI ではプリセットをドロップダウンで選ぶだけにする（= ワンポチ化の鍵）
- 合成後の**最終値**がマニフェストに書き出される。UE 側に「暗黙の既定値」を持たせない
- 出力環境（§10.4）は**最後に畳み込む**。強さは
  プリセット → `onepochi_asset.json` → UI / コマンドラインの明示指定 の順

### 10.3 `dccLayout` — DCC データフォルダの構造（R-1 の解決）

アセット元データフォルダ（§4.1）のサブフォルダ名とファイル名を**コードから追い出した**。

```jsonc
"dccLayout": {
  "fbxSubdir":       "fbx",
  "texturesSubdir":  "textures",
  "substanceSubdir": "substance",
  "houdiniSubdir":   "houdini",
  "manifestName":    "onepochi.json",
  "reportName":      "ue_report.json"
}
```

| キー | 既定 | 用途 |
|---|---|---|
| `fbxSubdir` | `fbx` | FBX とマニフェストの出力先 |
| `texturesSubdir` | `textures` | UE に持っていくテクスチャ |
| `substanceSubdir` / `houdiniSubdir` | `substance` / `houdini` | 作業データ（UE には持っていかない） |
| `manifestName` | `onepochi.json` | マニフェストのファイル名 |
| `reportName` | `ue_report.json` | UE 側レポートのファイル名 |

- **アセット単位で上書きできる。**`onepochi_asset.json` に `dccLayout` を書けばそのアセットだけ構造を変えられる
- **`export.outputSubdir` は廃止**し、`dccLayout.fbxSubdir` に統合した（同じ意味の設定が2つあるのをやめた）
- 実装: `presets.dcc_layout()` / `presets.asset_subfolder()` / `presets.asset_config_name()`

### 10.4 `destination.environments` — Dev / 本番の切り替え（R-2 の解決）

**書き込み先ルートを環境として宣言し、選んで切り替える。**

```jsonc
"destination": {
  "environment": "dev",                 // ★ 既定は dev（フェイルセーフ）
  "environments": {
    "dev":        { "contentRoot": "/Game/_Dev", "pathWhitelist": ["/Game/_Dev"] },
    "production": { "contentRoot": "/Game",      "pathWhitelist": ["/Game"] }
  },
  "pathTemplate": "{contentRoot}/{assetName}"
}
```

| 環境 | `contentRoot` | `pathWhitelist` |
|---|---|---|
| **`dev`（既定）** | `/Game/_Dev` | `["/Game/_Dev"]` |
| `production` | `/Game` | `["/Game"]` |

実測の展開結果（プリセット `prop` / アセット名 `Crate_01`）:

| 環境 | 出力先 |
|---|---|
| `dev` | `/Game/_Dev/Props/Crate_01` |
| `production` | `/Game/Props/Crate_01` |

**既定を `dev` にしたのは意図的なフェイルセーフ**（明示的に指定しない限り本番には書かない）。
選択経路は3つ:

| 経路 | 指定方法 |
|---|---|
| プリセット / `onepochi_asset.json` | `destination.environment` |
| Blender UI | ドロップダウン「**出力環境**」。`production` を選ぶと**赤い警告行**が出る |
| headless / CI | `run_headless.py --environment dev|production` |

- 選ばれた環境は**マニフェストの `destination.environment` に記録される**（[03 §6](03_マニフェスト仕様.md)）。
  UE 側はこれをレポートに残せる
- 未定義の環境名を指定した場合は `ValueError` になり、**ルール V-105** として日本語で報告される
  （使える環境名を列挙して返す）
- 実装: `presets.apply_environment()` / `presets.environments()` / `presets.environment_names()` /
  `presets.resolve_destination_path()`
