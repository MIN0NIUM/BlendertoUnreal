### 0.2 ユーザーの実行中セッションへの影響

**影響なし。** 調査はすべて `--background`（headless）の**別プロセス**で行いました。

- 起動中の Blender（PID 9744 / 5.2.0 LTS）には一切アクセスしていません
- `--factory-startup` でユーザー設定・アドオンを読み込まず、環境設定も変更していません
- `--disable-autoexec` で .blend 埋め込みスクリプトの自動実行を抑止しています
- ファイルの保存・書き換えは一切行っていません（読み取りのみ）
- スクリーンショット系・レンダリング系ツールは未使用（テキスト取得のみ）

### 0.3 当初予定していた手段と、切り替えた理由

| # | 手段 | 結果 |
|---|---|---|
| 1 | MCP `mcp__blender__*_for_cli` 系ツール（`get_blendfile_summary_path_info_for_cli` 等） | **失敗**。`Blender executable not found at 'blender'. Set the BLENDER_PATH environment variable` |

| 3 | `blender.exe --background --python` を直接実行 | **成功**。手段 1 と同じ「headless 別プロセス」という隔離条件を満たすため、これを採用 |

> **ツールチェーンへの申し送り**: MCP の `*_for_cli` 系を使うには、`blender-mcp` 起動時の環境変数に
> `BLENDER_PATH=C:\Users\user\Documents\Blender\stable\blender-5.2.0-lts.fbe6228777e7\blender.exe`

### 3.3 【重要】寸法・原点位置の検証

想定は「1m 立方体、原点 = 底面中心、-Y 側に向きが分かる特徴」でした。**実測結果は想定と一部異なります。**

#### ローカル／ワールド境界（location が原点なので両者一致）

| 軸 | 最小 | 最大 | 幅 |
|---|---|---|---|
| X | `-0.5` | `+0.5` | `1.0` |
| Y | **`-0.837828`** | `+0.5` | **`1.337828`** |
| Z | `-0.5` | `+0.5` | `1.0` |

#### 検証結果

| 想定 | 判定 | 実測の根拠 |
|---|---|---|
| 1m 立方体 | **△ 部分的に不一致** | 立方体**本体**は X/Y/Z すべて 1.0 m。ただし -Y 側の突起を含む全体 `dimensions` は **`(1.0, 1.337828, 1.0)`** で、**Y が 1.338 m** |
| 原点 = 底面中心 | **✗ 不一致** | Z 範囲は `-0.5 … +0.5`。**底面は Z = -0.5** にあり、原点は**底面から 0.5 m 上（= 本体の高さ中心）** |
| 原点 = バウンディングボックス中心 | **✗ 不一致** | Y のみ非対称（`-0.837828 … +0.5`）。bbox 中心は Y = `-0.168914` なので、原点は bbox 中心から **+Y に 0.168914 m** ずれている |
| 原点 = 立方体本体の中心 | **✓ 一致** | 突起を除いた立方体部分は X/Y/Z すべて `-0.5 … +0.5` で、原点はその幾何中心 |

> **結論**: 原点は **立方体本体の幾何中心**（Blender の `Add > Cube` 既定原点のまま）です。
> **底面中心ではありません。** 底面中心にするには原点を Z 方向に `-0.5` 移動する必要があります。
> → この差分は UE 取り込み後の配置基準に直結するため、`90_オープン課題.md` で方針確定が必要です。

### 3.4 -Y 側の「向きが分かる特徴」の実測

軸ごとの離散座標値：

| 軸 | 出現する座標値 |
|---|---|
| X | `-0.5`, `-0.16435`, `0.0`, `+0.16435`, `+0.5` |
| Y | `-0.83783`, `-0.5`, `+0.5` |
| Z | `-0.5`, `-0.16435`, `0.0`, `+0.16435`, `+0.5` |

これと位相数（頂点 13 / 辺 24 / 面 13 / ループ 48、面は三角形 4 + 四角形 9）から、形状は以下と**確定**できます。

```
立方体本体（8 頂点・5 面）
  + -Y 面を インセット した正方形リング（4 頂点, Y = -0.5, X/Z = ±0.16435）→ 四角形 4 面
  + その中心から -Y 方向に突き出した頂点 1 個（0.0, -0.837828, 0.0）→ 三角形 4 面
```

| 項目 | 実測値 |
|---|---|
| 突起の形状 | **四角錐（-Y 面に生えた「鼻」）** |
| 突起の底辺（インセット正方形） | 一辺 `0.3287 m`（`±0.16435`）、Y = `-0.5` 平面上 |
| 突起の頂点座標 | `(0.0, -0.837828, 0.0)` |
| 突起の突出長 | **`0.337828 m`**（立方体 -Y 面からの距離） |
| 凸性 | **非凸**（13 面中 8 面が凸条件を満たさず） |

頂点数 `8 + 4 + 1 = 13` ✓ / 辺数 `12 + 4 + 4 + 4 = 24` ✓ / 面数 `5 + 4 + 4 = 13` ✓
オイラー標数 `V - E + F = 13 - 24 + 13 = 2` → **閉じた多様体**（穴・開口なし）

> Blender の -Y は、一般的な FBX 軸変換では UE の +X（前方）に対応すると考えられますが、
> **UE 5.8 での実際の軸マッピングは 要検証** です（`docs/02` の方針に従い断定を避けます）。

## 7. ワンポチツール実装への示唆

実測から判明した、実装時に注意すべき点です。

### 7.1 単位・スケール

- **4 ファイルすべて `METRIC` / `scale_length = 1.0` / `METERS`** で統一されている。単位変換の特殊処理は現時点で不要
- ただし `scale_length` は**バリデーション必須項目**にすべき。`1.0` 以外だと FBX 出力時のスケールが狂う
- `dimensions` は `rotation_euler` を反映しない。**回転未適用の検出に `dimensions` は使えない** → `rotation_euler` / `matrix_world` を直接見る
- **負スケールは `dimensions` やワールド境界では検出できない** → `matrix_world.determinant() < 0` で判定する（`broken_negscale` と `木 箱` で実証済み）
- スケール未適用の検出は「`scale != (1,1,1)`」で足りる（`broken_scale` は `(2,2,2)`）。ただし `(-1,1,1)` のように**絶対値が 1 の負スケール**は `abs()` 比較では見逃すため、符号と絶対値を分けて判定する

### 7.2 原点の扱い（最重要）

- `01_static_minimal` の `Crate_01` の原点は、想定されていた**底面中心ではなく、立方体本体の幾何中心**（底面から +0.5 m）
- 全 4 ファイル全オブジェクトの `location` が `(0, 0, 0)` であり、**原点位置に関する意図が読み取れるサンプルが存在しない**
- → 「UE 取り込み時の原点基準（底面中心 / 重心 / Blender 原点そのまま）」は `90_オープン課題.md` で確定が必要。確定後、サンプル側の原点も揃えるべき
- `dimensions` のうち `(1.0, 1.337828, 1.0)` の **Y = 1.338 m は向き識別用の四角錐を含んだ値**。「1 m 立方体」としてサイズ検証すると不一致になる。検証は**立方体本体の境界**か、突起を除外した寸法で行う

### 7.3 命名

- **オブジェクト名とメッシュデータ名が一致していない**（`Crate_01` → `Cube`、`broken_scale` → `Cube`、`木 箱` → `Cube.003`）
  - マニフェストにどちらを記録するか（または両方か）を明確にする必要がある
  - FBX 出力時にどちらがノード名になるかで UE 側のアセット名・マテリアル割当が変わる → **要検証**
- **コリジョン名のパース曖昧性**: 規約は `<Prefix>_<対象メッシュ名>_<2桁連番>`（`docs/04 §2.3`）だが、
  対象メッシュ名が `Crate_01` のように `_数字` で終わると、`UCX_Crate_01_01` は
  - 「対象 = `Crate_01`、連番 = `01`」
  - 「対象 = `Crate`、連番 = `01_01`」（不正）

  のどちらとも読める。**右端の `_\d{2}` を連番として剥がし、残りを対象メッシュ名とする**実装（右から貪欲でないマッチ）に統一し、さらに
  **剥がした対象名がシーン内に実在するかを検証**すべき
- マテリアル名は `01`〜`03` では `M_` 準拠（`M_Crate_Body`, `M_Slot_A/B/C`）だが、`90` では Blender 既定の `Material`。
  **既定名（`Material`, `Material.001`, `Cube`, `Collection`）はバリデーションで警告対象にする**価値がある
- `93_broken_name` の `木 箱` は **日本語 + 半角スペース**の 2 問題を同時に含む。
  文字種チェックは「許可文字 `[A-Za-z0-9_]` 以外を全部検出して、何が違反か列挙する」実装にすると
  エラーメッセージが具体的になる（UI 文言は日本語 → Q-18）

### 7.4 コレクション構成

- `01` / `02` / `03` は **Blender 既定名 `Collection` のまま**。コレクション名に意味を持たせる設計（LOD コレクション方式 → Q-11）とは相性が悪い
- `02` では **レンダメッシュとコリジョンが同一コレクションにフラット配置**されており、役割の分離は**命名プレフィックスのみ**に依存している
  - → 「コレクションで分離」か「命名で分離」かを方針として確定する必要がある。現サンプルは**命名方式**を前提にしている
- `90` は **`<2桁番号>_<問題の種類>` 形式のコレクション名**（`90_broken_scale` 等）で、1 コレクション = 1 不具合 = 1 オブジェクトに整理されている
  - これはバリデータの**自動テストに非常に使いやすい構成**。テストコードは「コレクション名から期待されるエラー種別を導出 → バリデータ出力と照合」という形で書ける
  - ただし `93_broken_name` の `木 箱` は**負スケールも併発**しているため、「1 コレクション = 1 不具合」の前提でテストを書くと誤判定する。この 1 件だけ例外処理が必要（またはサンプルを修正）
- 全ファイルで**コレクションの入れ子は深さ 1**。深い階層を扱うコードパスは現サンプルでは検証できない

### 7.5 コリジョン

- `UCX_Crate_01_01` は **非凸**（レンダメッシュの -Y 四角錐がそのまま残り、13 面中 8 面が凸条件を満たさない）
  - `UCX_` は凸包を意味するため、**DCC 側バリデーション（方針 D-3）で凸性チェックを実装する価値が高い**
  - 凸性は「全頂点が各面の平面の内側（または上）にあるか」で安価に判定できる（本調査で実証）
  - UE 側がこれをどう解釈するか（自動凸包化するか、そのまま使うか）は **要検証**
- コリジョンメッシュに**不要なデータが付いている**: `UCX` にマテリアルスロット（`M_Crate_Body`）、両方に UV レイヤー
  - エクスポート前の整形（方針 D-4 の複製オブジェクト上）で、コリジョンからマテリアル・UV を除去する処理を入れるとよい
- `UBX_Crate_01_01` は **マテリアルスロット 0 個なのに面の `material_index` が 0** を指している
  - スロット数 0 のメッシュを FBX 出力したときの挙動は **要検証**
- コリジョンはレンダメッシュより大きい（UCX 約 1.0364 倍、UBX 1.12 m 立方体）。
  「コリジョンがレンダメッシュを包含するか」のチェックは実装可能だが、現サンプルでは UCX が -Y 方向に `0.868309` まで伸びており正しく包含している

### 7.6 マテリアルスロット

- `03_static_multislot` の 3 スロットは**すべて実際に使用されている**（面数 `11 / 1 / 1`）。未使用スロットのサンプルはない
- 3 マテリアルの `diffuse_color` が**すべて同一（既定のグレー）**。UE 取り込み後の検証は見た目ではできず、**スロット名と index** で行う必要がある
- マテリアルスロットの `link` は全オブジェクト `DATA`（オブジェクト単位のオーバーライドなし）。`OBJECT` リンクの扱いは未検証
- **スロット index と `mesh.materials` の順序は一致**していることを実測で確認（`[M_Slot_A, M_Slot_B, M_Slot_C]`）。マニフェストには index 順の配列として記録してよい

### 7.7 メッシュデータ

- **全メッシュが UV 1 枚のみ**（`UVMap`）。`90_broken_all` の `broken_nouv` だけ 0 枚
  - UE の Lightmap 用 2 枚目 UV を自動生成するかどうかは、サンプルからは判断できない（→ 仕様確定が必要）
- UV は全メッシュで U `0.125 … 0.875` / V `0.0 … 1.0` → **0-1 範囲内**。範囲外 UV のサンプルはない
- **全メッシュ カスタム法線なし（`has_custom_normals = False`）、頂点カラーなし、全面フラットシェード**
  - カスタム法線・頂点カラーを扱うコードパスは現サンプルでは検証できない
  - **注意**: Blender 4.1 で Auto Smooth が削除され、`mesh.auto_smooth_angle` は**存在しない**。スムーズ情報は
    `sharp_face`（FACE / BOOLEAN 属性）と辺の `use_edge_sharp` にある。Blender 4.1 未満を想定したコードは動かない
- **N-gon なし**（面サイズは三角形と四角形のみ）。三角形化（方針 A3）の検証には N-gon サンプルが必要
- 三角形数は `mesh.loop_triangles` と `Σ(len(poly.vertices) - 2)` の**両方で一致**した。後者は `loop_triangles` の計算が不要なので軽量

### 7.8 サンプル拡充の提案

現サンプルでは検証できない領域（→ §1 および §6.8 参照）:

1. **Skeletal Mesh サンプル**（Armature + ボーン階層 + 頂点グループ）が 1 つもない
2. **ソケットサンプル**（`SOCKET_*` Empty、`docs/04 §2.4`）が 1 つもない。Empty オブジェクト自体が全ファイルに存在しない
3. **LOD サンプル**（`_LOD0` / `_LOD1` …、`docs/04 §2.2`）がない。LOD 命名・コレクション方式（Q-11）の判断材料がない
4. **モディファイア未適用**のサンプルがない（全オブジェクト モディファイア 0 個）
5. **非一様スケール**（`(1, 2, 3)` 等）・**ゼロスケール**のサンプルがない
6. **原点が意図的にずれている**サンプルがない（全オブジェクト `location = (0,0,0)`）
7. **N-gon / 非多様体 / 重複頂点**のサンプルがない
8. **UV 範囲外 / UV 2 枚目欠落 / 未使用マテリアルスロット**のサンプルがない
9. **テクスチャ付きマテリアル**がない（実テクスチャ画像が 0 個）。テクスチャのコピー・UE 側取り込み経路が未検証
10. `01`〜`03` は原点基準が確定していないため、**原点方針の確定後にサンプルを作り直す**必要がある可能性が高い

### 7.9 ツールチェーンへの申し送り

- MCP の `mcp__blender__*_for_cli` 系ツールは、**`blender-mcp` サーバ起動時に `BLENDER_PATH` が必要**。
  未設定だと `Blender executable not found at 'blender'` で全滅する
  - 設定値: `C:\Users\user\Documents\Blender\stable\blender-5.2.0-lts.fbe6228777e7\blender.exe`

  - `C:\Users\user\Documents\Blender\stable\blender-5.2.0-lts.fbe6228777e7` ← 起動中・本調査で使用
