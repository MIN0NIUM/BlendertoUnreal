## 2. 失敗時のルール（ユーザー指示）

1. **同じタスクで3回失敗したら、そのタスクを中断する。**粘らない
2. 中断したら、**原因調査をサブエージェントに投げる**（テキストベースのみ）
3. 原因の切り分け:
   - **ユーザーの作業が必要** → 何をしてほしいかを具体的に指示として書く

4. サブエージェントに投げられる仕事は投げる（トークン節約）

## 3. 既知の落とし穴（実測ベース）

### P-1. Bash ヒアドキュメントで長い日本語 Markdown を書くと失敗することがある

- 症状: `cat > file <<'EOF' ... EOF` が `unexpected EOF while looking for matching` で失敗
- 発生: 2026-10-09、`docs/02_仕様書.md` の作成時
- 対策: **1KB を超える Markdown / JSON は `Write` ツールで書く。**Bash ヒアドキュメントは短いファイル・追記のみに使う

### P-2. `jq` がこの環境に無い

- `which jq` → 無し。フックや JSON 処理で `jq` を前提にしない
- JSON の検証は `python -c "import json; ..."` が使える（確認済み）

### P-0. Blender のオブジェクト複製は `.001` が付き、FBX のノード名を壊す

- 症状: 複製したオブジェクトが `UCX_Crate_01_01.001` になり、**UE のコリジョン命名規約が成立しない**
- 原因: Blender はオブジェクト名を一意に保つため、元が存在する限り複製は必ずサフィックスを得る
- 発生: 2026-10-10、`prepare.py` の初版
- 対策: 複製後に **元を `__onepochi_orig__<名前>` へ一時退避 → 複製に元の名前を付ける**。
  `cleanup()` で必ず戻す（`prepare.PreparedScene.renamed_originals`）
- **検証方法**: 書き出した FBX を Blender に読み戻してノード名を確認する
  （`bpy.ops.wm.fbx_import` が Blender 5.x で使える）。
  回帰テスト: `tools/dcc_blender/tests/test_integration_blender.py`

### P-0b. 値オブジェクトのコンストラクタ引数を渡し忘れる

- 症状: 退避した元オブジェクトの名前が復元されず、`__onepochi_orig__Crate_01` が残り続ける。
  2回目の書き出しが失敗する
- 原因: `renamed_originals` を組み立てたのに `PreparedScene(...)` に**渡していなかった**
- 発生: 2026-10-10
- 対策: **「元シーンを汚さない」系の不変条件は必ず結合テストで機械的に検証する。**
  目視レビューでは見落とす。`test_integration_blender.py` がこのバグを即座に検出した

### P-1b. Blender が複数バージョン入っている

- 実測: `5.2.0-lts.fbe6228777e7` と `5.2.2-lts.d13f752e3b9c` の2つが
  `~\Documents\Blender\stable\` に存在する（**どちらでも全テスト通過**）
- 対策: `tools/run_tests.py` / `tools/launch_blender.bat` は**新しい方を自動選択**する。
  特定バージョンで試したいときは環境変数 `BLENDER_EXE` を使う

### P-3. 新規作成した `.claude/settings.json` のフックは、そのセッションでは発火しない

- 症状: フック単体テストは通るのに、実際のツール呼び出しで発火しない
- 原因: 設定ファイルの監視は、**セッション開始時に存在していたディレクトリ**のみが対象。
  セッション中に `.claude/` を新規作成した場合は読み込まれない
- 発生: 2026-10-10、Git 禁止フックの導入時
- 対策: ユーザーに **Claude Code の再起動**（または対話ターミナルで `/hooks` を一度開く）を依頼する。
  それまでは**自己規律で禁止事項を守る**

### P-4. Git Bash は UE のアセットパスをファイルパスに変換してしまう

- 症状: `/Game/_Dev/Samples/...` を引数で渡すと、UE 側に
  `C:/Program Files/Git/Game/_Dev/Samples/...` が届く
- 原因: MSYS2 / Git Bash の自動パス変換。先頭が `/` の引数をドライブパスに書き換える
- 発生: 2026-10-10、往復テストの実行時
- 対策: **`MSYS_NO_PATHCONV=1` を付けて実行する。**
  UE パスを引数で渡すときは Git Bash ではなく **PowerShell か job.json** を使うほうが安全
- ※この事故は**バリデータ（V-004）が正しく検出した**。検証層が効いている証拠なので、
  「バリデータが止めた」ときは**まず自分のコマンドを疑う**

### P-5. `StaticMeshEditorSubsystem` は commandlet モードでは取得できない

- 症状: `unreal.get_editor_subsystem(unreal.StaticMeshEditorSubsystem)` が **`None` を返す**
- 発生条件: `UnrealEditor-Cmd.exe -run=pythonscript`（headless / commandlet）
- 影響: `get_lod_count` / `get_number_verts` / `get_simple_collision_count` /
  `get_lod_build_settings` が**すべて使えない**
- 対策: **`StaticMesh` 自身のメソッドを使う**（commandlet でも動作確認済み）。
  `get_num_lods()` / `get_num_triangles(0)` / `get_num_vertices(0)` / `get_num_sections(0)` /
  `get_num_tex_coords(0)` / `get_num_nanite_triangles()` / `get_bounding_box()`。
  コリジョン数は `body_setup.agg_geom` の `convex_elems` / `box_elems` / `sphere_elems` / `sphyl_elems` の長さで数える
- **Build Settings の適用は commandlet では不可**（エディタ UI 経由なら可能。要検証）

### P-6. `AssetImportTask` 経由の Interchange は非同期で、生成物が取れない

- 症状: `imported_object_paths` が**空のまま返る**。しかしアセット自体は生成されている
  （ログに `Built static mesh /Game/...` が出る）
- さらに: **保存前のパッケージはアセットレジストリに載らない**ため、
  `list_assets` の前後差分でも拾えない
- 対策: **`InterchangeManager.import_asset(destination_path, source_data, parameters)` を使う。**
  こちらは**同期**で、戻り値は bool ではなく**生成オブジェクトの参照文字列の配列**。例:
  `["/Script/Engine.MaterialInstanceConstant'/Game/.../M_Crate_Body.M_Crate_Body'", "/Script/Engine.StaticMesh'/Game/.../SM_Crate_01.SM_Crate_01'"]`
- 「戻り値が bool だろう」と決めつけて `if result:` だけで判定しないこと

### P-7. UE の終了コードは成否判定に使えない

- 症状: インポートが成功していても `UnrealEditor-Cmd.exe` が終了コード **`1`** を返す
- 原因: 空プロジェクトでも **GameFeatureData の既知エラー**が出るため
- 対策: **判定はレポート JSON（`ue_report.json` の `comparison`）で行う。**
  終了コードは参考情報としてログに残すだけにする

### P-8. サンプルはオブジェクト名が全部同じ → UE の出力先を分けないと壊れる

- 症状: コリジョン数の計測値がサンプルごとに累積していく
- 原因: `01` / `02` / `03` の**いずれもオブジェクト名が `Crate_01`**。
  UE の出力先が同じだと**同じアセットに上書きされ、コリジョンが累積する**
- 発生: 2026-10-10、往復テストの実装時（実際に一度踏んだ）
- 対策: 出力先を **`S01_Minimal` / `S02_Collision` / `S03_Multislot`** に分ける。
  サンプルを増やすときも**出力先はサンプル単位で分離する**

### P-9. Windows の既定コンソール（cp932）に日本語を出すと、サブプロセスが無言で死ぬ

- 症状: `tools/run_tests.py --with-ue` の E2E 往復テストだけが失敗する。
  **出力が1行も出ない**ので原因が分からない。単体で `python -X utf8 tools/run_roundtrip_test.py`
  として実行すると成功する
- 原因: `subprocess` で起動された Python の stdout が **cp932** になり、
  `✔`（U+2714）などの文字で `UnicodeEncodeError` を出して**最初の print で死ぬ**
- 発生: 2026-10-10、全テストの結合実行時
- 対策: スクリプト側で自衛する。各エントリポイントの冒頭で
  `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` を呼ぶ
  （`_force_utf8_stdout()` として実装済み）。
  **呼び出し側に `-X utf8` を要求する設計にしない**
- 教訓: 「出力が何も出ない」ときは**エンコーディングを疑う**。
  例外すら表示されないので、普通のデバッグでは見つけにくい

### P-10. 自動生成された Material Instance は保存しないと参照が切れる

- 症状: StaticMesh だけを保存すると、UE を開き直したときマテリアルが外れる
- 原因: **Interchange は FBX のマテリアルから `MaterialInstanceConstant` を自動生成する**
  （`material.mode = "none"` でも生成される）。メッシュはそれを参照するが、
  保存対象に含めていなかった
- 対策: `InterchangeManager.import_asset` の戻り値に含まれる**すべてのアセットを保存する**
  （`importer.save_all()`）
- 補足: 自動生成された MI の名前は Blender のマテリアル名（`M_xxx`）のままで、
  命名規約（`MI_` プレフィックス）に反する。レポートに警告を出すようにした。
  規約に沿った MI が必要なら `material.mode = "createInstances"` を使う

### P-11. FBX は「関節の位置」しか持たない — 末端ボーンの長さは往復で保存されない

- 症状: Blender で `bone_02` の長さを 0.25 m にして書き出し、FBX を読み戻すと **0.35 m** になる
  （実測: S-04 / Blender 5.2.2 / `add_leaf_bones=False`）
- 原因: FBX はボーンを「head→tail の線分」ではなく **関節（ノード）のトランスフォーム**として持つ。
  子を持たないボーンは tail の位置を表現する手段が無く、インポータが推定する
  （親の長さを流用するなど）
- 影響: **マニフェストの `lengthCm` を UE 側の検証項目にしてはいけない。**
  末端ボーンでは必ず不一致になる
- 対策:
  - ボーンに `isLeaf` を持たせ、**末端の長さは比較対象から外す**（マニフェスト v0.3.0）
  - 往復で保存されるのは **ボーン名・親子関係・head の位置**。検証はこれで行う
- 教訓: 「Blender で見えている数値」と「FBX が持てる情報」は同じではない。
  **往復で保存されない量を仕様の検証項目に入れない**

### P-12. Armature だけを選択すると書き出し対象が空になる

- 症状: Skeletal Mesh の検証で `V-001 書き出し対象のメッシュが1つもありません` が出る。
  シーンにはメッシュがあるのに空になる
- 原因: 収集は選択オブジェクトを起点にする。`.blend` に **Armature だけ選択された状態**が
  保存されていると、メッシュが1つも集まらない
  （S-04 の保存済み選択状態が `['Armature']` だった）
- これは**テストの都合ではなく実運用の問題**: Skeletal Mesh では
  「Armature を選んでボタンを押す」のが自然な操作
- 対策: 選択にメッシュが無く Armature がある場合、
  **その Armature にスキンされたメッシュを拾い直す**（`collect.meshes_skinned_to()`）。
  アセット名もそこから決める
- 教訓: サンプルファイルの**保存済み選択状態**は、実際のユーザー操作を再現する
  貴重な入力。「テストだから選択が変」で片付けない

### P-13. リネーム時は `__pycache__` を消す

- パッケージ名を変えた（`wanpochi` -> `onepochi`）あと、古い名前の `.pyc` が残っていると
  import が食い違う
- 対策: リネームスクリプトの先頭で `__pycache__` を再帰的に削除する（実施済み）

### P-14. テストにスキーマのバージョンをハードコードしない

- 症状: マニフェストを v0.3.0 に上げたら `test_minor_version_difference_warns` が落ちた。
  「隣のマイナーバージョン」として `0.3.0` を直書きしていたため、
  それが**本番のバージョンになった瞬間に意味を失った**
- 対策: `manifest_io.SUPPORTED_SCHEMA_VERSION` から機械的に隣のバージョンを作る。
  フィクスチャの `schemaVersion` も実装の定数を使う
- 教訓: バージョンに依存するテストは**実装の定数から導出する**


### P-15. UE の Python プロパティ名は「スタブが無いと導出値」になる

> **2026-10-11 追記: Skeletal Mesh については実機で確定した。**
> `probe_skeletal_api.py` が **applied 22 件 / failed 0 件**、
> 実際の取り込みでも `pipeline.applied` **20〜21 件 / failed 0 件**。
> つまり `onepochi_ue/skeletal.py` の導出名（snake_case 第1候補）は
> **すべて正しかった**。
>
> ただし **(a) 確定したのは「名前」だけ**（取り込み結果の正しさは往復テストで別途検証。
> S-04 / S-05 / S-06 で確認済み → docs/12 §4.6）、
> **(b) 実測はすべて GUI エディタ（Remote Control 経由を含む）**であり
> **commandlet モードは未確認**。P-5 の前例があるので別物として扱う。
>
> **候補名を順に試す構えは外さない。**UE のバージョンが上がれば名前は変わりうる。
> 以下の記述は「スタブが無い環境ではこう扱う」という手順として有効。

- 事実: この環境には **UE の Python スタブ（`Intermediate/PythonStub/unreal.py`）が生成されていない**。
  スタブは Python プラグインの *Developer Mode* を ON にしてエディタを起動したときだけ作られる
- そのため、ヘッダの C++ 名（例 `bImportSkeletalMeshes`）から Python 名（`import_skeletal_meshes`）を
  **手で導出**することになる。導出規則自体は `PyGenUtil.cpp` の
  `PythonizePropertyName` / `PythonizeName` で確定しているが、
  **略語や数字の境界**（`bUseMikkTSpace` / `bUseT0AsRefPose` など）で外す可能性がある
- さらに: `EditAnywhere` だけのプロパティは **Python の属性にならない**。
  属性になるのは `BlueprintReadWrite` / `BlueprintReadOnly` 等が付いているものだけ
- **対策**: 設定は必ず `set_editor_property()` で行い、**候補名を順に試す**。
  `set_editor_property()` は Python 名が解決できないとき**生の C++ FName にフォールバックする**ため、
  `("import_skeletal_meshes", "bImportSkeletalMeshes")` の順で試せばどちらでも通る
  （`onepochi_ue/skeletal.py` の `set_any()`）
- **どの名前が通ったか・通らなかったかを必ずレポートに残す。**
  「設定したつもりで効いていない」が最悪のパターン（P-5 / P-6 と同根）
- 検証用プローブ: `tools/ue_plugin/probe_skeletal_api.py`。
  UE の Output Log から `py "<path>"` で実行でき、**アセットを作らない**
- 教訓: UE の Python API は**スタブを見るまで確定しない**。
  スタブが無い状態で書いたコードは「要検証」であることを明示し、
  プローブを同梱する

### P-16. UE のエディタが開いている間は commandlet を走らせない

- `UnrealEditor-Cmd.exe <uproject>` は同じプロジェクトを**別インスタンスで開く**。
  GUI エディタが開いたままだとアセットや DDC の書き込みが競合しうる
  （`tools/import_via_ue_cmd.bat` にも同じ警告を書いてある）
- そのため**ユーザーが UE を起動している間は往復テストを実行しない**。
  代わりに:
  - 読み取りだけのプローブは **UE の Output Log から `py` で実行してもらう**（同一プロセスなので安全）
  - 本番経路は Remote Control API（これも同一プロセス）
- 教訓: 検証したい気持ちより**ユーザーの作業中セッションの保護**が優先。
  実行できないときは「実行できない理由」と「ユーザーが安全に実行する手順」を渡す

> **2026-10-11 追記: 制約は解消した。**Remote Control 経由で往復テストを回せる。
>
> ```bash
> python tools/run_roundtrip_test.py --via-rc        # 起動中のエディタに依頼する
> python tools/run_tests.py --with-ue --via-rc       # 全テスト（ボタン経路も含む）
> ```
>
> **`--via-rc` を付け忘れると commandlet が起動して競合する。**
> UE が起動しているときは必ず付ける。逆に UE を閉じているときは
> `--via-rc` なしの従来経路を使う（RC につながらないので即座に止まる）。

### P-17. Interchange は `SOCKET_` 命名からソケットを**自前で作る**（しかも値が壊れている）

- 症状: ポストプロセスでソケットを作ると、UE 側に**同名のソケットが2個**できる。
  `find_socket()` が返すのは**インポータ製**のほうなので、
  自分で作った正しい値が見えない
- 実測（S-08 / UE 5.8.3 / `SOCKET_Lid`）: インポータ製の値は

  | 項目 | インポータ製 | 正しい値（マニフェスト宣言） |
  |---|---|---|
  | location | `(0, -0, 100)` | `(0, 0, 100)` ✅ 一致 |
  | rotation (roll, pitch, yaw) | `(-76.2103, -15.6831, 20.228)` | `(-13.7897, 15.6831, 20.228)` |
  | scale | **`(100, 100, 100)`** | `(1, 1, 1)` |

  **scale に単位換算の 100 倍が混入している**（ソケットに付けたものが 100 倍になる）。
  roll は Blender の X 回転から **90° を引いた値**で、pitch の符号も逆
- これは `UCX_` のコリジョンと同じ構図（K-2 / C-7）。
  **インポータが規約を honor してくれるのは良いことだが、値が信用できない**
- 対策: 方針 D-6 のとおり**インポータ製を消して宣言値で作り直す**
  （`postprocess.remove_existing_sockets()`）。消すのは
  **マニフェストが宣言した名前だけ**にして、UE 側で手で足した別名のソケットは残す
- **重複の検知方法**: `StaticMesh.sockets` は protected で読めないが、
  **`get_sockets_by_tag("")` で全ソケットを列挙できる**（実測）。
  `find_socket()` は先頭1個しか返さないので、
  **総数を実測しないと「2個になった」事故を見逃す**
- 教訓: 「インポータが作ってくれた」ものは**値まで実測する**。
  存在確認だけで合格にしない

### P-18. 戻り値が `void` の UE API を `attempt()` の None で判定すると1回で止まる

- 症状: 同名ソケットを「無くなるまで消す」ループが**1個消して抜ける**。
  重複が残り続ける
- 原因: `postprocess.attempt()` は失敗時に `None` を返す設計。しかし
  `StaticMesh.remove_socket()` は**成功しても `None`（void）**なので、
  `if attempt(...) is None: break` が成功を失敗と読む
- 発生: 2026-10-11、ソケット重複の修正時（**自分で入れたバグ**）
- 対策: **void の API は戻り値で成否を判断しない。**進捗は別の観測で確かめる
  （この例では `find_socket()` が `None` を返すこと）。
  ループには必ず上限を付け、上限に達したらレポートに残す
- 教訓: `attempt()` のような「失敗を None にする」ヘルパは、
  **void を返す API と組み合わせると嘘をつく**。使う前に戻り値の有無を確認する

### P-19. `UCX_<名前>_<数字>` の切り分けは文字列だけでは決まらない

- 症状: `UCX_Crate_01` が **V-041（本体メッシュ `Crate` が無い）**で止まる。
  本体は `Crate_01` なのに
- 原因: 末尾の `_01` を**連番として剥がす**実装だった。
  しかし `<名前>_<2桁>` は本プロジェクトの標準的なメッシュ名（`Crate_01`）なので、
  `UCX_Crate_01` は
  **(a) 本体 `Crate_01` の連番なし / (b) 本体 `Crate` の 1 番**の
  どちらにも読める。**文字列だけでは決められない**
- 発生: 2026-10-10、S-08 の実測時
- 対策: `parse_collision_name(name, known_bodies)` に
  **書き出し対象の本体メッシュ名の一覧を渡し、実在する読み方を優先する**。
  どちらも実在しないときは従来の規則で返して V-041 に判定させる
- 教訓: 命名規約のパーサに**曖昧さが残る**なら、
  文字列の中だけで解こうとせず**文脈（実在する名前の集合）を渡す**

### P-20. UE エディタが起動している間は `Content/` をファイルシステムから消さない

- 往復テストは `Content/_Dev` を `shutil.rmtree` でクリーンにしていた。
  **これはエディタが閉じているときだけ安全**。開いている間に消すと
  メモリ上のパッケージと食い違い、保存時に復活しうる（X-6 の趣旨）
- 対策: `--via-rc`（エディタ起動中）では
  **`EditorAssetLibrary.delete_directory()` で UE 自身に消させる**
- 補足: **保存されていない新規パッケージは Python から消せない。**
  `delete_asset()` / `delete_directory()` がどちらも `False` を返す
  （実測。`collect_garbage()` のあとでも同じ）。
  調査用の一時アセットを作ったら、**その場で消さずに済む置き場**
  （= 保存しないまま UE を閉じる）を前提にする

### P-21. Blender ではオブジェクト名を重複させられない — 規約が実現不可能だった

- 症状: [docs/04](04_命名規約.md) §2.2 の「LOD 間でオブジェクト名が同じでよい
  （コレクションで区別される）」が **そもそも Blender で実現できない**
- 実測（Blender 5.2.2 LTS / headless）: `bpy.data.objects` の名前は**ファイル全体で一意**。
  2 個目に `obj.name = "Crate_01"` を代入しても**例外は出ず、黙って `Crate_01.001` になる**。
  `name_full` も `.001` 付き。メッシュデータ名も同じ。**コレクションは名前空間を作らない**
- さらに `.001` は `naming.name_problem()` が「名前にドットが含まれています」で弾くため
  **V-003 エラー**になり、回避策にもならない
- 発生: 2026-10-11、N-4（S-07 修正版サンプルの生成）
- 対策: **LOD0 は素のアセット名（`Crate_01`）、LOD1 以降は `<アセット名>_LOD<n>`。**
  LOD レベルの判定は `naming.parse_lod_collection()`（**コレクション名だけ**）で行い、
  オブジェクト名からは判定しない。オブジェクト名は `levels[].sourceNode` に記録するだけ
- 教訓: 「コレクションで区別すればよい」は **DCC のデータモデルを確認せずに書いた規約**だった。
  **命名規約を決めるときは DCC 側で 1 回作ってみる**（headless なら 10 行で確かめられる）

### P-22. `lod.levels` に LOD0 が入っていなかった（仕様書と実装の食い違い）

- 症状: 3 段 LOD を書き出しても `staticMesh.lod.levels` が **2 件**（LOD1 / LOD2 のみ）。
  [docs/03](03_マニフェスト仕様.md) §11.4 は「`LOD0` 必須・欠番はエラー」で、
  本文のサンプルにも `level: 0` が載っている
- 原因: `bl/pipeline.py` が `if lod.level == 0:` を
  「main FBX の記録」と「levels への追加」の**排他の分岐**にしていた。
  LOD0 は `assets[].sourceFile` にしか現れなかった
- 影響: UE 側が `levels` だけを見ると**どの FBX が LOD0 か決められない**
- 発生: 2026-10-11、N-4 の書き出し確認時
- 対策: LOD0 も `levels[]` に積む。ただし `mode` の自動切替は
  **`len(levels) >= 2` を条件にする**（無条件に `manual` にすると
  LOD0 しか無いアセット（S-01 / S-08）のプリセット既定が壊れる）。
  UE 側（`lod.normalize_levels`）は **LOD0 が有っても無くても動く**ようにした
- 教訓: **スキーマが許す形 ≠ 仕様書が要求する形。**
  仕様書が「必須」と書いた要素は、**実際に書き出した JSON を目で見て**確認する

### P-23. UE Python の構造体配列は、要素を取り出すと**コピー**になる

- 症状: `material.mode = createInstances` で **`MI_Slot_A` は生成されるのに、
  メッシュのスロットにはインポータ製の `M_Slot_A` が割り当たったまま**。
  しかもコードは成功を返す（`set_editor_property` が `True`）
- 実測（UE 5.8.3 / `StaticMesh.static_materials`）:

  | 方式 | 結果 |
  |---|---|
  | `arr = mesh.get_editor_property("static_materials")`<br>`arr[0].set_editor_property("material_interface", mi)`<br>`mesh.set_editor_property("static_materials", arr)` | **効かない**（`M_Slot_A` のまま） |
  | 同じ手順 + **`arr[0] = s` で代入し直す** | **効く**（`MI_Slot_A` になる） |
  | `unreal.StaticMaterial()` を新規に作って `arr[0] = fresh` | 効く（ただし `material_slot_name` 等を自分で引き継ぐ必要がある） |

- 原因: `TArray<FStruct>` の要素は**値型**。`arr[0]` は毎回**新しいコピー**を返すため、
  そのコピーを書き換えても配列の中身は変わらない
- 影響（**同じバグが 3 か所にあった**）:
  - `materials.apply_material_slots()` の MI 割当 — P5 の本体が効いていなかった
  - `postprocess.apply_material_slot_names()` のスロット名変更 —
    **一度も効いていなかった**。FBX 由来の名前がたまたま同じだったので
    `comparison.materialSlots` が緑のままで気づけなかった（**K-8 の典型**）
  - `reimport._restore_materials()` の復元
- 対策: `postprocess.update_struct_in_array(sink, array, index, properties)` に集約し、
  **書き換えたら必ず `array[index] = struct` で代入し直す**。
  さらに**書き戻したあと読み直して実測**し、食い違ったら警告を出す
- 教訓: **「設定したつもりで効いていない」は戻り値では分からない**（P-15 / P-18 と同根）。
  値を変える API は**必ず読み直して確かめる**。
  そして「比較項目が緑」＝「処理が効いている」ではない。
  **既定値と期待値が同じテストは、何も検証していない**

### P-24. 「設定の保持」と「データの更新」を混ぜると、作り直したものが反映されない

2回目の取り込み（再インポート）を実機で回して出た**2つの事故**の記録。
どちらも「`reimportPolicy` が保持側に倒す」ことの副作用で、
**1回目は緑なのに2回目で壊れる**ので気づきにくい。

#### (a) インポータが自動生成したコリジョンが、2回目から残り続ける

- 症状: LOD サンプルを**2回**取り込むと `comparison.collisionShapes` が
  `期待 0 / 実測 1（convex）` で落ちる。1回目は 0 で通る
- 原因: `collision.simple = "none"` の削除処理（`clear_simple_collision`）は
  **apply 側**にある。`preserveSettings` では `collision` が preserve に回るので
  削除が走らず、**インポータが毎回作る凸包1個が残る**
  （[docs/12](12_実装状況.md) C-7 / I-8: Interchange は `UCX_` が無い FBX にも凸包を1個作る）
- 対策: `reimport._restore_collision()` で
  **「スナップショットが 0 個なのに増えていたら消す」**ようにした。
  *0 個への復元は実装できる*（形状を作り直す必要がない）。
  スナップショットが 1 個以上あって増えた場合は**増えた分だけを選んで消す手段が無い**ので、
  正直に警告だけ出す
- 教訓: **「復元できない」と諦める前に、復元できる特殊ケースを切り出す。**
  `0 個に戻す`は作り直しが不要なので可能だった

#### (b) `mode = "manual"` の LOD が、2回目から更新されない

- 症状（**設計の誤り**）: アーティストが Blender で LOD1 を作り直して再インポートしても、
  `lod` が preserve に回るため **`import_lod` が呼ばれず、古い LOD1 が残る**
- 判断: **`lod` には2つの意味が混ざっている**
  - `mode = "manual"` の `levels[].sourceFile` は **DCC 側が持つデータ**（ジオメトリ）
  - `mode = "auto"` の自動生成や画面占有率は **UE 側の設定**
  「設定を保持する」方針をデータにまで適用すると、**上流で作り直したものが届かない**
- 対策: **`mode = "manual"` のときは `preserveSettings` でも LOD を適用する。**
  適用した事実と理由をレポート（`assets[].lod.appliedDespitePreserve`）と警告に残す。
  UE 側の LOD を守りたい場合は**マニフェストで `mode` を `"none"` にする**
  （`"none"` のときは既存 LOD を一切触らない）
- 実測（再インポート時）: `importedLevels: [1, 2]` / `lodCount` 3 /
  三角形数 [1280, 320, 80] が維持される
- 教訓: **「保持」の対象は設定だけ。**上流（DCC）が真であるものを保持対象に入れると、
  ツールが更新を止める側に回ってしまう。
  新しいカテゴリを `reimportPolicy` に足すときは
  **「これは UE 側で人が決めるものか、DCC 側が決めるものか」**を先に答える

> **副産物**: Interchange の再インポートは **LOD0 だけを差し替える**ことが分かった。
> LOD1 以降のスロットは残る（`lodCountBefore` 3 → `lodCountAfter` 3）。
> つまり「再インポートで LOD が消える」心配は無い。消えるのは
> **LOD1 以降を更新したいのに更新されない**という逆向きの事故だった。

### P-25. 「やらなくて済む仕事」の判定は、道具を取る前に済ませる

- 症状: `textures.import_textures()` が**取り込み済みのテクスチャを `failed` に入れる**。
  2枚目以降のスロットで同じテクスチャを参照すると全部失敗扱いになる
- 原因: `done`（既取り込みの再利用判定）を **`_interchange_manager()` を取った後**に
  書いていた。取り込み機構が不要なケースなのに、機構が無いと即 `failed` に落ちる
- 発生: 2026-10-11、N-7 の単体テスト（**テストが先に見つけた**）
- 対策: `if not pending: return` を**道具の取得より前**に置く
- 教訓: UE 依存部を「道具が無ければ全部失敗」で書くと、
  **道具が要らない経路まで巻き込む**。フェイクの `unreal` を差し込んだ
  単体テストはこの種のバグを拾える

### P-26. UE の enum は `int()` できない / `TC_Default` は値 **0**

**2つとも「偽になりうる正しい値」を失敗と混同する話**（P-18 と同根）。

- 対策: enum 値の取得は必ず **`is not None`** で判定する。

### P-27. **ツールが作った**アセットも、自分で保存しないと参照が切れる

### P-28. 仕様の表を実装にコピーしたら、テストで突き合わせる

### P-29. Remote Control の設定は `DefaultEngine.ini` からは読まれない（→ Python 実行が再起動後に拒否される）★解決済み

- 症状: 前のセッションでは通っていた `--via-rc` が、**UE エディタを再起動した翌日に拒否された**

  ```
  Object Default__PythonScriptLibrary cannot be accessed remotely,
  check remote control project settings.
  ```

- 実測（2026-10-13 / UE 5.8.3）: 保存済みの設定ファイル
  `UEProject/OnePochiPlayground/Saved/Config/WindowsEditor/RemoteControl.ini` には
  **必要な値が入っている**のに拒否される

  ```ini
  bRestrictServerAccess=True
  bEnableRemotePythonExecution=True
  CustomAllowedRemoteFunctionCalls=(ClassPath="/Script/PythonScriptPlugin.PythonScriptLibrary",
                                    FunctionName=("ExecutePythonCommandEx"),bAllowChildClasses=False)
  ```

- 疑っている原因（**要検証**）:
  - `CustomAllowedRemoteFunctionCalls` は配列プロパティ。`.ini` に `+` 無しの1行で
    書かれているため、起動時に配列へ読み込まれていない可能性がある
  - `AllowlistedClients` が **`192.168.1.1`〜`255.255.255.255`** で、
    **`127.0.0.1` が範囲外**。`bRestrictServerAccess=True` との組み合わせを疑う余地がある
  - 設定は `Saved/Config`（= ユーザー単位・エディタ終了時に書かれる）にあり、
    `Config/DefaultEngine.ini`（= プロジェクトに commit される側）には**入っていない**
- 当面の対策: **ユーザーに Project Settings から入れ直してもらう**（A-18）。
  設定の変更はツールからは行わない（アプリ設定の変更はユーザーの領分）
- 恒久対策の候補（**未実施 / 要検証**）:
  `Config/DefaultEngine.ini` に `[/Script/RemoteControlCommon.RemoteControlSettings]` として
  **`+CustomAllowedRemoteFunctionCalls=(...)`** を書き、プロジェクト側の設定として固定する。
  チーム配布でも同じ問題が出るので、**ここは docs/13 P6（運用）の課題として残す**
- 教訓: **「一度やってもらった設定」は再起動で消えうる。**
  実機検証の前提になる設定は、**設定ファイルのどこに書かれるか**まで確認して
  プロジェクト側（commit される側）に寄せる。
  そうでないものは「毎回確認が必要な前提」として手順書に書く

#### 2026-10-13 夜の追加実測 — **原因が1つに絞れた**

エディタ再起動後も拒否されたので、**段階的にプローブして切り分けました**
（`python tools/check_rc_config.py` が同じ切り分けを再現します）。

| 段 | 試したこと | 結果 |
|---|---|---|
| ① | `GET /remote/info` | **200**（サーバは動いている） |
| ② | プロパティ読み（`EditorStyleSettings.SelectionColor`） | **200** |
| ③ | 非 Python 関数の呼び出し（`KismetSystemLibrary.GetEngineVersion`） | 400 `Executing function ... is not allowed by remote control settings` |
| ④ | `PythonScriptLibrary.ExecutePythonCommandEx` | 400 **`Object Default__PythonScriptLibrary cannot be accessed remotely`** |

**②が 200 だったことで、前回の疑いが2つ消えました**:

- **`AllowlistedClients` はシロ。**`127.0.0.1` は範囲（`192.168.1.1`〜）の外なのに**読み書きが通る**
  → この許可リストは loopback を弾いていない。**だから触らない**（根拠の無い変更をしない）
- **`bEnforcePassphraseForRemoteClients` もシロ。**パスフレーズヘッダ無しで 200 が返る

**③と④でエラーメッセージが違う**ことが決定的でした。③は「**関数**が許可リストに無い」、
④は「**オブジェクト**に遠隔アクセスできない」＝ **より手前の、Python 専用のゲート**。
つまり原因は `CustomAllowedRemoteFunctionCalls` ではなく
**`bEnableRemotePythonExecution` が実行時に効いていないこと**です。

**原因が確定しました（2026-10-13 深夜 / エンジンのソースで裏取り）**。
`Config/DefaultEngine.ini` に書いた設定は **1つも読まれていませんでした**。

```cpp
// UE_5.8/Engine/Plugins/VirtualProduction/RemoteControl/Source/
//   RemoteControlCommon/Public/RemoteControlSettings.h:180
UCLASS(config = RemoteControl)
class REMOTECONTROLCOMMON_API URemoteControlSettings : public UDeveloperSettings
```

`config = RemoteControl` なので、この設定クラスは **`RemoteControl.ini` 階層からしか読まれない**。
正しい置き場所は **`Config/DefaultRemoteControl.ini`**。
`DefaultEngine.ini` に同じセクションを書いても**完全に無視される**（エラーも警告も出ない）。

> **見抜く手がかりは最初から出ていました。**UE がユーザー設定を書き出す先が
> `Saved/Config/WindowsEditor/**RemoteControl**.ini` という名前だった。
> UE はこのファイル名を `UCLASS(config = ...)` の指定から作る。

### P-30. `os.path.basename()` は Blender の相対パス（`//` 始まり）に使えない — Windows で空文字が返る

- 症状: 新しく足した検証ルール **V-114**（`_N` の色空間が `Non-Color` か）が**黙って出ない**。
  例外も警告も出ず、**何も起きない**形で壊れた（2026-10-13 / M-2 の実装中）
- 原因: Blender の画像パスは `//textures/T_x.png` という**独自の相対パス**。
  Windows の `ntpath` はこれを **UNC パス（`//サーバ/共有`）と解釈**し、
  `splitdrive()` が文字列全体をドライブ部とみなすため、
  **`os.path.basename("//textures/T_x.png")` が `''` を返す**（実測 / Python 3.13 / Windows 11）

  ```python
  >>> import os
  >>> os.path.basename("//textures/T_x.png")   # Windows
  ''
  >>> os.path.basename("//textures/T_x.png")   # Linux / macOS
  'T_x.png'
  ```

  **プラットフォームで挙動が変わる**ので、Linux の CI では気づけない
- 対策: Blender のパスは標準ライブラリのパス関数に**素通ししない**。自前で切る

  ```python
  name = path.replace("\\", "/").rsplit("/", 1)[-1]
  ```

  （`tools/dcc_blender/addons/onepochi/bl/validate.py: image_colorspace_of()`）
- 回帰テスト: `tests/test_validate.py: test_image_colorspace_of_handles_blender_relative_paths`
  （`//` 付き / バックスラッシュ区切り / 絶対パスの 3 系統を固定）
- 教訓: **P-15 / P-18 / P-23 と同根。「値が合わない」ではなく「何も起きない」形で壊れる。**
  新しい検証ルールを足したら、**実サンプルで発火することを必ず確認する**
  （S-11 で V-113 / V-114 が実際に出たことを確認して初めて気づいた）

### P-32. レポートの入れ物の形を推測で書くと、サンプルが来るまでバグが眠る

- 症状: `importer.py` が生成済みテクスチャのパスを集める箇所で、
  テクスチャを1枚でも取り込むと **`AttributeError: 'list' object has no attribute 'get'`**。
  **取り込み自体は成功していて、保存の直前で落ちる**（いちばん惜しい失敗の仕方）

  ```python
  # 誤り: material["textures"] を dict として扱っていた
  created_textures = [t.get("assetPath") for t in
                      ((entry.get("material") or {}).get("textures") or {})
                      .get("imported", [])          # ← list に .get() を呼ぶ
                      if isinstance(t, dict) and t.get("assetPath")]
  ```

- 原因: `materials.apply_material_slots()` の `record["textures"]` は
  **スロットごとの list**で、各要素の `imported` が
  `import_slot_textures()` の記録（dict）。入れ物が**二段**になっている。
  書いた側は dict 一段だと思い込んでいた
- **なぜ 2026-10-14 まで誰も踏まなかったか**: `textures` が空リストのときは
  `or {}` が効いて `{}` になり、`.get("imported", [])` が通ってしまう。
  **テクスチャを持つサンプルが S-11 まで無かったので、分岐に入らなかった**
- 教訓1: **他のモジュールが作る記録の形は、読む側が実装を見て確かめる。**
  `record = {...}` の初期化行を見れば list か dict かは 1 行で分かる
- 教訓2: **`or {}` は「空なら安全」に見えて、型の間違いを隠す。**
  list を期待する場所では `or []` にする。そうすれば
  「空のとき通って、中身があると落ちる」という最悪の形にならない
- 教訓3: **新しい要素を足したら、それを使うサンプルを必ず1本通す。**
  単体テストは通っていた（記録を作る側と使う側が別々にテストされていた）。
  **端から端まで1回通すまでは「動いた」と言えない**（K-8 と同じ精神）
- 検出のしかた（UE を起動せずに再現できた）:

  ```bash
  python -c "
  rec = {'textures': [{'index':0,'imported':{'paths':['/Game/a']}}]}
  ((rec or {}).get('textures') or {}).get('imported', [])"
  # AttributeError: 'list' object has no attribute 'get'
  ```

### P-33. UE の enum をレポートに入れると、取り込みは成功しているのにレポートだけ消える

- 症状: S-11（テクスチャ）の往復テストで、**取り込み自体は成功**しているのに最後に落ちた。

  ```
  ✖ 取り込み中に予期しない例外:
     TypeError: Object of type TextureCompressionSettings is not JSON serializable
     File "...onepochi_ue/importer.py", line 962, in import_from_manifest
       write_report(report_path, report)
  ```

- 原因: `textures.observed_texture_settings()` が `compression_settings` を**読み直した生の値**
  （`unreal.TextureCompressionSettings` の enum オブジェクト）を、そのまま
  `verified["compression"]` としてレポートに入れていた。
  `json.dump` は UE の型を知らないので落ちる
- **いちばん損な失敗の仕方**: UE 側の処理は全部終わっていて、
  **証拠（レポート）だけが残らない**。往復テストから見ると「失敗」に見えるが、
  アセットは正しく生成されている。原因の切り分けを誤りやすい
- 対策（2つ入れた）:
  1. **記録は JSON 安全な形にする。**`textures.jsonable()` を追加し、
     enum は `name`（`TC_NORMALMAP` など）に落とす。
     **比較は生の値のまま**行う（enum 同士で比べないと一致判定が壊れる）
  2. **保険として `json.dump(..., default=str)`。**
     値を正しい形で入れるのは呼び側の責任だが、
     **1つの値のために証拠を全部失うよりは文字列化する**
- 教訓: **UE から「読み直した」値は、そのままレポートに入れない。**
  P-23 で「書いたら読み直して確かめろ」と決めたが、
  **読み直した値は UE の型なので、記録に入れる前に素の型へ落とす**必要がある。
  P-23 とセットで覚える
- 見つけ方: 単体テストでは出ない（テストは dict を自作するので enum が出てこない）。
  **実機で1回通すまで分からない型**だった（P-32 と同じ構図）
