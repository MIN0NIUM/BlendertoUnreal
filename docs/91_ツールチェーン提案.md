# ワンポチツール — 開発ツールチェーン提案書

## 要約（結論）

- **UE 5.8 には Epic 公式の MCP プラグイン（`ModelContextProtocol` + `AllToolsets`）が同梱されており、Claude Code から直接エディタを駆動できる。サードパーティの `unreal-mcp` 系 OSS を新規導入する理由はほぼ消滅した。**
- **Epic 公式の Claude Code プラグイン `unreal-engine-skills-for-claude-code`（MIT / Anthropic 公式マーケットプレイス掲載）を入れるのが最短ルート。** 30 以上の Toolset／数百ツールが使えるようになる。
- 本プロジェクトの中核である「インポート処理そのもの」は、公式 MCP の `AssetTools` / `StaticMeshTools` / `SkeletalMeshTools` に加え、**UE Python（`AssetImportTask` / Interchange パイプライン）で自作するのが本線**。Remote Control API（30010）は冗長なので採用しない。
- Blender 側は**既に接続済みの `mcp__blender__*` で十分**（`execute_blender_code` + API ドキュメント検索を持つ）。`ahujasid/blender-mcp` 等の重複導入は不要。
- 差分価値は「自作 Skill」で出す。**UE 命名規約チェック / Interchange パイプライン設定 / FBX エクスポート事前検証 の 3 本**を最優先で作る。

## 1. Unreal Engine 向け MCP サーバ / Claude 連携

### 1-1. 【本命】Epic 公式 Unreal MCP プラグイン（UE 5.8 同梱）

UE 5.8 のリリースノートに「With Unreal Engine 5.8, we bring a new experimental **MCP (Model Context Protocol)** plugin for the Unreal Editor」と明記されており、**エディタプロセス内に MCP サーバが立つ**。これが本プロジェクトの基盤になる。

- **何ができるか**: MCP クライアント（Claude Code / Cursor / MCP Inspector）がローカル HTTP 経由でエディタを駆動。アクタ生成、ライティング設定、マテリアルインスタンス作成、Slate ウィジェット検査、オートメーションテスト実行などが Tool として露出。
- **エンドポイント**: 既定で `http://127.0.0.1:8000/mcp`。HTTP + SSE のみ対応（**WebSocket / stdio は非対応**）。ループバック以外の接続は拒否、**認証レイヤなし**（リモート公開不可）。
- **有効化手順**:
  1. `Edit > Plugins` で **Unreal MCP** を有効化（依存の `Toolset Registry` は自動有効化）。
  2. **All Toolsets** プラグインも有効化（これがないとツールが機能しない）。エディタ再起動。
  3. `Edit > Editor Preferences > General > Model Context Protocol` で **Auto Start Server** を ON。
  4. コンソールで `ModelContextProtocol.GenerateClientConfig ClaudeCode` を実行 → `.mcp.json` が生成される。
- **主要コンソールコマンド**:
  - `ModelContextProtocol.StartServer [port]` / `ModelContextProtocol.StopServer`
  - `ModelContextProtocol.RefreshTools`（ツールプロバイダ再ポーリング）
  - `ModelContextProtocol.GenerateClientConfig ClaudeCode`
- **UE 5.8 時点の Toolset**: 公式ドキュメントに挙がっているのは `SceneTools` / `ActorTools` / `MaterialInstanceTools` / `ObjectTools`、および `GASToolsets` の `AttributeSetToolset`。第三者がまとめた 5.8.0 のカタログでは **52 Toolset**。本プロジェクトに効くのは:
  - `editor_toolset.toolsets.asset.AssetTools`（21 ツール / プロジェクト内アセットとディスク上ファイルの操作）
  - `editor_toolset.toolsets.static_mesh.StaticMeshTools`（16 ツール）
  - `editor_toolset.toolsets.skeletal_mesh.SkeletalMeshTools`（22 ツール）
  - `animation_toolset.toolsets.import_export.SequencerImportExportTools`（6 ツール / アニメーションデータの import・export）
  - 出典: https://tc-imba.github.io/ue-official-mcp/references/toolsets/
  - **要検証**: `AssetTools` に「ファイルからのインポート」ツールが含まれるかは未確認（`find_assets` の存在は確認できた）。Interchange / FBX 専用 Toolset は**このカタログには見当たらない**。実機で `list_toolsets` / `describe_toolset` を叩いて確認すること。
- **導入コスト**: 低（同梱プラグインの ON + コンソール 2 コマンド）。
- **本プロジェクトで使えるか**: **使える。基盤として必須。** ただし「Static/Skeletal Mesh の *インポート* 自体」は公式 Toolset に露出していない可能性が高いため、2-2 / 1-5 の自作 Toolset で埋める前提で設計する。
- **注意**: Epic 自身が「experimental」「incomplete in places」「APIs and data formats may change」「not designed for remote use」と明言。UE 5.8 は UE5 系の最終予定メジャーリリース（5.9 はオプション扱い）という文脈も踏まえ、API 変更に追従できる薄い抽象層を自作側に置くこと。

### 1-2. 【本命】Epic 公式 Claude Code プラグイン

### 1-4. Remote Control API（HTTP 30010 / WebSocket 30020）

- UE 内部に Web サーバを立て、REST 風 API で HTTP / WebSocket リクエストを処理する公式機能。`Plugins > Messaging` の **Remote Control API** を有効化。
- 既定ポート: **HTTP 30010**、**WebSocket 30020**（Project Settings の Web Remote Control で変更可）。
- `http://localhost:30010/remote/object/call` に POST して UObject の関数を呼べる。Python スクリプトから HTTP リクエストを投げる使い方も可能。
- ドキュメント:
  - クイックスタート: https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-control-quick-start-for-unreal-engine
  - WebSocket リファレンス: https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-control-api-websocket-reference
  - プラグイン API インデックス: https://dev.epicgames.com/documentation/unreal-engine/API/PluginIndex/RemoteControl
- **評価**: 技術的には「Blender 側から直接 UE を叩く」構成が組めるため、**Claude を介さない純粋なツール実装としては有力な選択肢**。ただし公式 MCP が同じ外部制御ニーズを満たすため、二重の経路を抱えるコストが高い。**結論: 本プロジェクトでは採用しない。**ただし「UE エディタを起動せず commandlet でバッチインポートしたい」要件が出たら、Remote Control ではなく **commandlet + UE Python** を選ぶ。

### 1-5. 自作 Python Toolset（これが本プロジェクトの「ワンポチ」の実体）

UE 5.8 の ToolsetRegistry は、`UToolsetDefinition`（Python では `unreal.ToolsetDefinition`）の派生クラスを収集し、Tool として印をつけた関数を公開する仕組み。**公式同梱 Toolset の多く（`SceneTools` / `ActorTools` / `MaterialInstanceTools` / `ObjectTools`）自体が Python で書かれている**ため、Python で自作するのが自然。

- **Python**: `unreal.ToolsetDefinition` を継承し、公開したいメソッドに **`tool_call` デコレータ**を付ける。
- **C++**: `UToolsetDefinition` を継承し、メソッドに **`AICallable`** マーカーを付ける。
- **雛形生成**: Claude Code の `unreal-mcp` プラグインの **`create-toolset` スキル**でスキャフォールドできる。
- **AgentSkill**: `unreal.AgentSkill` を継承して `instructions` 属性を持たせることで、「このツールをいつ使うか／正しい手順／よくある失敗／安全ルール／検証手順」をエンジン側のアセットとして同梱できる。`ToolsetRegistry.AgentSkillToolset` が skill の list / read / create・update ツールを提供する。
  - API リファレンス: https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/ToolsetRegistry/UAgentSkill
  - ヘッダ位置: `/Engine/Plugins/Experimental/ToolsetRegistry/Source/ToolsetRegistry/Public/ToolsetRegistry/AgentSkill.h`
- **本プロジェクトでの設計案**: `OnePochiImportToolset`（Python）を作り、
  - `import_static_mesh(file, dest_path, pipeline_preset)`
  - `import_skeletal_mesh(file, dest_path, skeleton, pipeline_preset)`
  - `validate_imported_asset(asset_path)`（命名・LOD・マテリアルスロット・コリジョン検査）
  を `tool_call` で公開。内部実装は後述の `AssetImportTask` / Interchange。これにより **Claude Code からも、UE の UI ボタンからも、同じ 1 関数が呼べる**。
- 参考解説: https://buckley-builds.com/blog/extending-unreal-engine-mcp/

## 2. Blender 向け MCP サーバ / Claude 連携

### 2-1. 【既導入】`mcp__blender__*`（本セッションに接続済み）

重複インストールは不要。既に以下が揃っている。

| ツール | 本プロジェクトでの活用 |
|---|---|
| `execute_blender_code` / `execute_blender_code_for_cli` | エクスポート処理本体の試作・実行。CLI 版は `blender --background` でのバッチ化検証に使える |
| `get_objects_summary` / `get_object_detail_summary` | エクスポート前のシーン検査（スケール・階層・モディファイア・マテリアルスロット） |
| `get_blendfile_summary_datablocks` / `_missing_files` / `_of_linked_libraries` / `_path_info` | 出力前バリデーション（リンク切れテクスチャ、外部ライブラリ依存の検出）— **ワンポチの事前チェックに直結** |
| `get_python_api_docs` / `search_api_docs` / `search_manual_docs` | `bpy` API の正確な引数名確認。推測コードを書かずに済む |
| `get_screenshot_of_window_as_image` / `render_viewport_to_path` / `render_thumbnail_to_path` | エクスポート結果の目視確認、UE 側サムネイルとの比較 |
| `jump_to_tab_by_name` / `jump_to_view3d_object_by_name` | UI 操作の自動化 |

**運用方針**: `execute_blender_code` は MCP サーバ指示にもあるとおり「最後の手段」。まず専用ツールで状態を読み、`search_api_docs` で API を確定してからコードを書く。これが品質に直結する。

### 2-2. `ahujasid/blender-mcp`（評価: 不採用 — 既導入分で足りる）

- ★約 26.8k〜30.2k（集計時期により差あり）/ fork 約 2.7k。MCP サーバとしては最も有名。

### 2-3. `EpicGames/BlenderTools`（Send to Unreal）— 参考実装として読む

本プロジェクトと**ほぼ同じ課題を Epic 自身が解いた前例**。車輪の再発明を避けるため、設計を読む価値が非常に高い。

- ★約 3.3k / fork 約 168 / MIT / 688 commits。
- **最新リリースは Send to Unreal 2.4.3（2023年11月9日）**。リリースノートの対応表記は「Tested on Blender 3.3, 3.6 and **Unreal 5.3**」。
- **メンテ状況: 正直に言って停滞気味。**リリースは約 3 年前が最後で、対応表記も Blender 3.x / UE 5.3 のまま。Blender 5.x / UE 5.8 での動作は**完全に要検証**。open issue 約 71 件。
- 技術的に重要な前例: **Send to Unreal は Blender の FBX エクスポートオペレータをそのまま呼んでおらず、FBX アドオンの `export_fbx_bin` モジュールのロジックにパッチを当てた版を使っている**。これは「素の `bpy.ops.export_scene.fbx` では UE 向けに足りない」ことの強い証拠。自作時は同じ落とし穴（ボーン軸、リーフボーン、スケール）を踏む前提で設計する。
- ドキュメント: https://epicgamesext.github.io/BlenderTools/
- **結論: 採用しない（stale すぎる）が、ソースは必ず読む。**特に `send2ue` の検証ロジックと命名規約の扱いは自作 Skill の仕様の下敷きにできる。

### 2-4. Blender 側の FBX エクスポート事情（2026年10月時点）

- **現行バージョンは Blender 5.2 LTS**（5.2 は 2026年7月13〜14日リリース、5.2.2 が 2026年9月15日。LTS サポートは 2028年7月まで）。5.3 は 2026年11月10日予定（2026年9月30日に Beta 入り）。
- **インポータ側**: 4.5 で実験導入された **C++ 製 FBX インポータが Blender 5.0 で既定**になった。Python 製の旧 FBX インポートアドオンは **legacy / deprecated**。アドオンは `bpy.ops.import_scene.fbx` → **`bpy.ops.wm.fbx_import`** へ移行するよう案内されている。
- **エクスポータ側**: **5.0 の Pipeline & I/O リリースノートにエクスポータの変更は記載されていない。**検索した範囲では 5.1 / 5.2 でも FBX エクスポータが C++ 化された形跡はなく、`File > Export > FBX` は引き続き Python アドオン（`bpy.ops.export_scene.fbx`、Forward / Up / Apply Scalings / Add Leaf Bones / Bake Animation オプション）が走る。
  - **要検証**: 「C++ 製 FBX エクスポータは 5.2 時点でも未提供」という点は、二次情報ベースの確認にとどまる。実機で `bpy.ops.wm.fbx_export` が存在するかを `search_api_docs` / `dir(bpy.ops.wm)` で**必ず直接確認**すること。
  - なお Blender 5.1 では「FBX shape key normals」関連の変更が入ったとされる（**要検証**）。
- リリースノート: https://developer.blender.org/docs/release_notes/5.0/pipeline_io/ / https://developer.blender.org/docs/release_notes/5.1/
- **本プロジェクトへの含意**: エクスポートは Python アドオン API（`bpy.ops.export_scene.fbx`）前提で書く。将来の C++ エクスポータ移行に備え、**エクスポート呼び出しを 1 関数に閉じ込める**。また glTF 経路（UE 側で Interchange が安定サポート）を**第二の出力先として最初から並走させる**設計が有利。

## 3. Claude Code の Skills / Plugins / サブエージェント機構の活用法

### 3-1. 機構の整理

- **Skill**: ディレクトリ + `SKILL.md`（YAML frontmatter + 本文）。配置先:
  - 個人: `~/.claude/skills/<name>/SKILL.md`
  - **プロジェクト: `.claude/skills/<name>/SKILL.md`（リポジトリにコミットして共有）← 本プロジェクトはこれ**
  - ネスト: `<subdir>/.claude/skills/<name>/SKILL.md`（そのディレクトリ配下で作業するときにロード）
  - プラグイン: `<plugin>/skills/<name>/SKILL.md`（`/plugin-name:skill-name` で呼べる）
- **主な frontmatter フィールド**: `name` / `description` / `when_to_use` / `allowed-tools` / `disallowed-tools` / `disable-model-invocation` / `user-invocable` / `paths`（glob で発動条件を限定）/ `arguments` / `model` / `effort` / `hooks` / `shell`（`bash` or **`powershell`**）/ `context: fork` + `agent`（サブエージェントで隔離実行）
- **文字列置換**: `$ARGUMENTS` / `$0` `$1` / `${CLAUDE_SKILL_DIR}` / `${CLAUDE_PROJECT_DIR}` / `${CLAUDE_SESSION_ID}` など。`${CLAUDE_SKILL_DIR}` は**同梱スクリプトを呼ぶのに必須**。
- **動的コンテキスト注入**: 本文に `` !`command` `` やコードフェンス `` ```! `` を書くと、送信前にシェルを実行して出力で置換できる。**Windows なら frontmatter に `shell: powershell` を指定**。
- **ライブリロード**: `~/.claude/skills/`、`.claude/skills/`、`--add-dir` 配下の `SKILL.md` 変更は即反映（トップレベルを新規作成した直後は `/reload-skills`）。

- **Hooks**: `.claude/settings.json`（プロジェクト, コミット可）/ `.claude/settings.local.json`（gitignore）/ `~/.claude/settings.json`（全プロジェクト）/ プラグインの `hooks/hooks.json` / Skill・Subagent の frontmatter。構造は `hooks.<Event>[].matcher` + `hooks[]`（`type`: `command` / `http` / `mcp_tool` / `prompt` / `agent`）。個別ハンドラに `if` を付けて権限ルール構文で絞り込める。

### 3-2. 本プロジェクトで作るべき自作 Skill（具体案）

**優先度 A（最初に作る 3 本）**

1. **`ue-naming-check`** — UE 命名規約チェック
   - 役割: Blender 側のオブジェクト／マテリアル／UV 名と、UE 側の最終アセット名が規約に合うか検証し、違反を列挙 + 自動修正案を出す。
   - 典拠: Epic 公式推奨（https://dev.epicgames.com/documentation/en-us/unreal-engine/recommended-asset-naming-conventions-in-unreal-engine-projects）と Allar スタイルガイド（`Prefix_BaseAssetName_Variant_Suffix`）。**`SM_` と `S_` の流派差**（Allar は Static Mesh に `S_` を推奨、業界的には `SM_` が多数派）を**プロジェクト規約として `CLAUDE.md` に明記**してから Skill に焼き込む。Skeletal Mesh は `SK_` が共通。
   - 実装: `${CLAUDE_SKILL_DIR}/check_naming.py` を同梱し、`shell: powershell` で起動。`paths` に `**/*.py` 等を指定して誤発動を抑える。
2. **`interchange-pipeline-setup`** — Interchange パイプライン設定
   - 役割: Static Mesh / Skeletal Mesh それぞれのパイプラインプリセット（`InterchangeGenericAssetsPipeline` 派生）を生成・適用し、Project Settings > Interchange のパイプラインスタックに登録する手順を定型化。
   - 典拠: https://dev.epicgames.com/documentation/en-us/unreal-engine/importing-assets-using-interchange-in-unreal-engine / https://dev.epicgames.com/documentation/en-us/unreal-engine/interchange-import-reference-in-unreal-engine
3. **`fbx-export-validate`** — FBX / glTF エクスポート事前検証
   - 役割: エクスポート前に `mcp__blender__get_objects_summary` 等で、単位スケール（`global_scale` / `apply_unit_scale` / `apply_scale_options`）、Forward/Up 軸、`bake_space_transform`、Add Leaf Bones、未適用モディファイア、リンク切れテクスチャ、マテリアルスロット数、UV チャネル数を一括チェック。
   - 典拠: https://docs.blender.org/api/current/bpy.ops.export_scene.html / Send to Unreal が `export_fbx_bin` にパッチを当てている事実。

**優先度 B（Phase 2 以降）**

4. **`ue-python-snippets`** — `AssetImportTask` / Interchange の正しい呼び方を固定（`async_` フラグ、`ScriptedImportAssetAsync` と非 reflected な `ImportAssetAsync` の違い等、ハマりやすい箇所を明文化）。
5. **`roundtrip-smoke-test`** — Blender → エクスポート → UE インポート → アセット検証 → スクリーンショット比較までを 1 コマンドで回す。`context: fork` でサブエージェント隔離実行にすると、長いログが親の文脈を汚さない。
6. **`dcc-abstraction-review`** — 将来の Maya / Houdini 対応を見据え、DCC 固有コードが抽象層を越えて漏れていないかをレビューする Skill（Houdini は `mcp__fxhoudini__*` が既に接続済みなので、実験はすぐできる）。

## 5. UE 5.8 固有の注意点

### 5-1. Interchange が既定のインポート経路

- **UE 5.4 以降、Interchange がレガシー FBX プラグインを置き換えて既定**になっている。FBX をインポートすると Interchange インポータが走る。
- **ただし公式ドキュメントのフォーマット成熟度表記では FBX は依然「Experimental」**、glTF（`.glb` / `.gltf`）/ MaterialX（`.mtlx`）/ USD（`.usd`）が安定扱い。「既定経路だが成熟度ラベルは Experimental」というねじれた状態なので、**FBX 一本足にしない設計（glTF 並走）がリスクヘッジになる**。
- Interchange の 3 要素: **Pipeline**（インポートデータへの処理の集合）/ **Pipeline Stack**（フォーマット別の順序付きパイプライン一覧。`Project Settings > Interchange` で設定）/ **Factory**（最終アセットを生成）。既定パイプラインは Asset / Material / Texture / Scene の各種で、プロパティ変更または `InterchangePipelineBase` のサブクラス化でカスタマイズ可能。**Blueprint / C++ / Python のいずれでもパイプラインを作れる**（Python は `InterchangePythonPipelineBase` + `@unreal.uclass()`）。
- 非対応フォーマットではエンジンが自動的にレガシーフレームワークへフォールバックする。

### 5-2. レガシー FBX インポータの扱い

- CVar **`Interchange.FeatureFlags.Import.FBX`** を `false` にするとレガシー FBX インポートに戻せる。レベルインポート側は **`Interchange.FeatureFlags.Import.FBX.ToLevel`**。
- **UE 5.8 のリリースノートにレガシー FBX インポータの廃止アナウンスは見つからなかった。**つまり当面は残る見込みだが、公式に「残す」と宣言されたわけでもない。
- **本プロジェクトの方針**: レガシー経路は使わない。ただし Interchange 側で再現できない挙動に当たったときの切り分け手段として CVar の存在は記録しておく。

### 5-3. UE 5.8 の FBX / USD 関連の実変更（リリースノートで確認できたもの）

- **FBX インポート性能（Experimental）**: 「FBX remains the main data format to import 3D models」「we performed stabilization work to support for the **uFBX library (Experimental)**」。**大量メッシュを含む重い `.fbx` のインポート時間が顕著に短縮**される。→ ワンポチツールの体感速度に直結するので、**有効化方法と有効／無効での計測を Phase 2 で必ず行う**（有効化手段の具体は**要検証**）。
- **USD は Interchange 経由でアセットインポートが production ready、レベルインポートは experimental**。USD ファイル読み込み時のスキーマハンドラの順序が公開・編集可能になり、USD トランスレータをコードで拡張して独自スキーマに対応できるようになった。
- **USD Pregen フレームワーク（Experimental）**: 参照 USD ファイルと生成された UE アセットの関係を追跡し、現行の孤立したコンポジションインポートで起きるフラット化・重複を防ぐ。→ 将来 USD 経路を採るなら重要。
- **Batch processor フレームワーク**: 複数ワーカーでの大規模アセット処理をサポート。→ 大量メッシュのバッチインポートで使える可能性あり（**要検証**）。

### 5-4. Python API の変更点（UE 5.8）

- **Python バージョンは 3.11.8**（VFX Reference Platform 準拠）。**要検証**: これは Python API ドキュメントの記述で、5.8 でのバージョン据え置きは明示確認できていない。
- **破壊的変更の記載は見つからなかった。**確認できた追加・改善:
  - Blueprint のエディタスクリプティング API が大幅拡張。グラフ編集は新しい **`unreal.BlueprintGraphEditor`** 経由、一般的な Blueprint 編集は **`unreal.BlueprintEditorLibrary`** の新関数経由。
  - **Optional property の Python からの読み書きが可能に**なった。
  - PCG に Python スクリプティング用ノード（**PCG Python Data Processor**）が追加。
  - エディタシャットダウン時、Python 環境が部分的に終了した状態で Python コールバックがクリーンアップされてクラッシュする不具合を修正。
- 実装上の注意（バージョン非依存だが頻出のハマり所）:
  - `AssetImportTask` は拡張子から適切なインポート処理を選び、**サポートされるフォーマット（obj / texture / gltf 等）では既定で Interchange を使う**。非同期インポートが可能なフォーマットでは **`async_`** 変数が使える。
  - `ImportAssetAsync` は reflected UFUNCTION ではない。**スクリプト向けの変種は `ScriptedImportAssetAsync`** で、`UInterchangeSourceData` オブジェクトを取る。
  - Interchange モジュールはインポートを非同期タスクで開始するため、`import_asset` は早期にリターンする。`importasset` / `importscene` は非同期にすべきでなく、非同期用には別関数がある。

### 5-5. UE 5.8 のポジション

- **UE 5.8 は UE5 系の最終予定メジャーリリース**（5.9 はオプション扱い）とされ、新システム追加より性能とコア機能の成熟に寄せた内容。→ **5.8 を安定ターゲットとして作り込む判断は妥当**。ただし UE6 への移行が視野に入るため、UE 依存部分（Toolset / Python）を薄く保つ価値は高い。

## 導入手順の提案（Phase 分け）

### Phase 0: 土台づくり（半日）

1. `C:\Users\user\Documents\_STUDY\BlenderToUnreal` に `CLAUDE.md` を作成。スコープ宣言（UE 側セットアップ・GC 化は対象外）、命名規約の確定（`SM_` / `SK_`）、「Interchange 既定・レガシー FBX 不使用」方針、Blender MCP の運用ルールを明記。
2. `.claude/settings.json` を作成（hooks は空でよい）。`.claude/skills/` ディレクトリを用意。
3. **Git Bash を PATH に通す**（Epic 公式 Claude Code プラグインの前提）。
4. Blender 側は既導入の `mcp__blender__*` の疎通確認のみ。`bpy.ops.wm.fbx_export` の存在有無をここで実測して記録。

### Phase 1: UE 側の AI 連携を開通（半日〜1日）

1. UE 5.8 プロジェクトで `Unreal MCP` + `All Toolsets` を有効化し再起動。
2. `Editor Preferences > General > Model Context Protocol` で Auto Start Server を ON。`127.0.0.1:8000/mcp` の疎通を確認。
3. コンソールで `ModelContextProtocol.GenerateClientConfig ClaudeCode` → 生成された `.mcp.json` をプロジェクトルートに配置。
4. `/plugin install unreal-engine-skills-for-claude-code@claude-plugins-official`
5. **`list_toolsets` / `describe_toolset` を実行して、`AssetTools` / `StaticMeshTools` / `SkeletalMeshTools` の実ツール一覧を記録**（インポート系ツールの有無をここで確定させる = 設計の分岐点）。

### Phase 2: エクスポート／インポートの核を作る（1〜2週間）

1. **Blender 側**: `export_static_mesh()` / `export_skeletal_mesh()` を 1 モジュールに実装。スケール・軸・リーフボーン・`bake_space_transform` の設定値をプリセット化。`get_blendfile_summary_*` を使った事前バリデータを同時に書く。glTF 経路も同じ関数シグネチャで並走させる。
2. **UE 側**: `AssetImportTask` ベースの `import_static_mesh()` / `import_skeletal_mesh()` を UE Python で実装。Interchange パイプラインプリセットを Static / Skeletal それぞれ作成し `Project Settings > Interchange` に登録。
3. **自作 Skill を 3 本作る**: `fbx-export-validate` / `interchange-pipeline-setup` / `ue-naming-check`。`skill-creator` で description の発動精度を eval。
4. **uFBX（Experimental）の有効化方法を調べて計測**。重いファイルでの効果を記録。

### Phase 3: 「ワンポチ」化（1週間）

1. UE 側に **自作 Python Toolset `OnePochiImportToolset`**（`unreal.ToolsetDefinition` + `tool_call`）を実装。Epic プラグインの `create-toolset` スキルで雛形生成する。
2. **`unreal.AgentSkill`** を 1 枚作り、「いつ使うか／正しい手順／よくある失敗／安全ルール／検証手順」をエンジン側に同梱。
3. Blender 側にオペレータ + UI ボタンを追加し、1 クリックで「検証 → エクスポート → UE インポート → 検証」が走る状態にする。
